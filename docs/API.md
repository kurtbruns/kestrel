# Kestrel API

The shape of Kestrel's authoring API: the rules every route follows, so a client that has learned one route can predict the rest. The spec (`docs/SPEC.md`) says what both clients can rely on; this document says the shape they rely on it through. The generated API reference, served in the admin surface and built from the route registration in `src/app.ts`, lists every route, field, and example, so this document names concepts and never restates a route. The reference opens with these rules in the words a client needs (`src/reference/concepts.ts`), and the refusal table below (`src/reference/refusals.ts`), because Claude reads the reference and never this document: a change to a principle or a code changes both in the same commit.

**Who this is for.** Whoever adds to the API or builds a client for it, human or Claude.

**Where it lives.** Every route of the API sits under `/api`, which is also the admin line: the editor at `/dashboard` and the API at `/api` are the publisher's, behind the access layer, and everything else is the public reader surface (SPEC §11). A new route goes under `/api` too, so it is gated with nothing for an instance to add. Before 1.3.0 the posts, sends, subscribers, and suppressions routes sat at the top level (`/posts`, and so on); those paths now answer `404`.

---

## Design principles

Kestrel has two clients, the web editor and Claude, and both act for one publisher (SPEC §1). They stay in step because they read and act through one API over one copy of the data, and neither keeps a rule of its own about what the data means. So the API carries the design, and it has two jobs. It never leaves a client believing something false: a retry, a race, or a late read still ends with the client holding the true state. And it can be learned from its reference alone, because Claude meets it cold in every conversation, and a concept only the editor's author understands is one Claude will use wrongly.

When the two pull against each other, the smaller API wins, with the expectation written down, as long as no invariant (SPEC §3) rests on the difference. Each principle below follows from these two jobs.

1. **One API, no private door.** The editor uses no route that Claude cannot, and no route exists only to serve the editor's layout. The one exception is the development tooling under `/api/dev/`, which exists only on a local instance.

2. **One shape per noun.** A resource reads the same on every route that carries it: in a list, alone, in the feed, and in the answer to an act or a refusal. A client keeps one copy of each resource and updates it from whichever answer arrives. A new route never invents a lighter or richer variant. A resource embeds only its own parts, as a subscriber's suppression sits inside the subscriber on every route, and refers to another resource by a reference, a shape of its own that is the same wherever it appears: a post's `send` is `{ id, status, fire_at, rev }`, whose `rev` tells a client that also holds the send's view, from the feed, whether that copy is current, and the whole send is one read away at `GET /api/sends/:id`. An answer or a refusal about other resources carries them whole, as an act's answer carries its resource: the sends a settings save would re-make (`in_use.sends`, `remake_required`, `remake_too_close`) and the ones it re-made (`remade`) are each the send's own view. A heavy part of a resource, such as a send's frozen email or its per-recipient rows, gets a route of its own rather than a second shape.

3. **The server decides, the client displays.** Whatever needs a rule to work out is worked out once, by the server, and carried on the resource: a send's `phase`, its `conditions` (what is wrong, in words to show as they stand), the `actions` a send and a post carry (exactly what the server would accept now, each with the method and path to use), and when to read again. A post's `actions` take in the deployment too, so neither offers to schedule a post while no provider is connected. A client never re-derives these from the raw fields. If it has to, the server is missing a field.

4. **An act is safe to repeat because of what it means.** Acting twice on the same decision is answered as done: canceling a canceled send, or moving a send to the time it already has, answers success with `changed: false`. A client that lost an answer simply sends the act again. Acts on a send carry no precondition naming the state the client saw. Both clients act for the same person, and the result shows at once in every answer. The review window (SPEC §6) is there for noticing, and a send act before the fire time can be undone. Saving a post is the one exception, and the reason is what would be lost: a save must carry the revision it was based on, and is refused without one or if another writer has saved since, because an overwritten paragraph is lost without anyone seeing it (SPEC §4). Erasing a subscriber is safe to repeat too: an erasure keeps the subscriber, stripped to the address (SPEC §7), so a repeat answers that subscriber as the first one left them and changes nothing.

5. **A refusal names the client's next move.** Every refusal has a status, a code, and a message written to be shown or relayed as it stands. A refusal about the request names the `field`. A refusal about a resource's state carries the resource as it now stands, so the client can redraw without a second read, and `retry_after` when waiting is the remedy: a post (`post_not_draft`, `slug_permanent`), the settings (`settings_changed`, `conflict`), a subscriber (an erasure's `run_in_progress`, an Add's `signup_required`), a suppression (`suppression_changed`), and a send, with the `cursor` to follow it from, as every answer about a send has. The exceptions are `plan_stale`, which carries no plan, since its remedy, planning again, is the read, and an import's `run_in_progress`, which carries no subscriber, since its remedy is to commit the same plan again. Codes are grouped by what the client does next (below). A new code is added only when a client would do something different for it. A new cause that calls for an existing remedy gets its own message, not its own code.

6. **Changes have one order, and it is a number.** Every change to a send, whoever or whatever made it, is a write that takes the next number in one sequence across all sends. A send's `rev` is the number of its last change, so of two copies the higher `rev` is newer. A read's `cursor` is the sequence number at that read, and "what changed since" is every change above it. The clock also changes how a send reads with no write, for example when a fire time passes. A read that follows changes therefore also carries every send whose state the clock is setting right now, whatever the cursor, and since at most a few sends are ever in such a state, the cost is negligible. A client that holds two copies at the same `rev` keeps the one it read later.

7. **Strict at the door.** A body that is not the declared type, a field of the wrong shape, an unknown query value, or a cursor this server did not issue is refused with a 400 that names the field. Nothing is dropped or defaulted, so a request is never answered with a success that ignored part of it. A route takes only what its registration declares: the router refuses a body field it doesn't list (at any depth of a nested one), a query parameter it doesn't list or that is given twice, and a value outside the set a parameter declares, before the handler runs, so a new route gets the check by declaring its fields and parameters. A reader page and a webhook are exempt, since a link in an email gathers parameters its reader never added. A cross-site request from a browser never reaches a handler (SPEC §11).

8. **Sized for one publication.** A publication has hundreds of sends and up to tens of thousands of subscribers (SPEC §1). Paging exists where a collection grows with the list: subscribers, suppressions, and a send's per-recipient rows. The list of sends pages too, because it sorts and filters. Following changes does not page either: it reads every change since the cursor, in order, and only caps how many one read carries, answering `more` when it stopped short, so a client reads again at once and still sees each change once. The export pages too, keyed on the address, so a list read across many pages while it changes still gives every address exactly once, and so do a subscriber's sends, keyed on fire time, so a send starting while they are read never repeats or skips one; an import takes at most a set number of rows, which the API states for the deployment. A keyed page answers `next`, which the client passes back as `after` until it is null. The server sets a keyed page's size, never the client, and where what a page costs depends on the deployment's plan, it sets it from the plan.

9. **A concept earns its place.** A new field, header, parameter, or code must change what some client shows or does. Before adding one, ask these questions:
   - Which client reads it, and what does that client do differently because of it?
   - Could an existing concept carry it: a condition, an action, a message, a `rev`?
   - Does it protect an invariant, or a race between two acts of the same person? If the latter, principle 4 applies.
   - Can it be explained in one sentence of the API reference?

10. **The manifest is the contract.** Each route is declared once, on the route manifest in `src/app.ts`: its method and path, its access tier, the body types it takes, its body fields and query parameters with the values a parameter takes, what it returns, the refusals it gives, and an example. Everything a client reads about the API is generated from that declaration: the reference the editor shows, its Markdown for an agent, the OpenAPI document, and `/llms.txt`. The router holds each request to the same declaration: the access tier decides the gate, and a body type, field, parameter, or value the route doesn't declare is refused before the handler runs (principle 7). So the reference can't promise a request the router won't take, and a client builds on what it says. A field, value, or refusal detail that isn't declared isn't part of the API, whatever a handler happens to answer, and changing the API means changing a declaration.

## Names on the wire

Every JSON field name and every enum value is snake_case: `fire_at`, `email_only`, `needs_attention`, in a request body and in an answer alike. A query parameter's name and value are snake_case too, and a list's `sort` is the name of the field it sorts by, a dotted path when that field is nested (`audience.count`), never a word from a column header. A path segment is a URL rather than JSON and keeps its own form (the reader-page ids, such as `not-an-email`). Claude writes a request from the reference, so one rule with no exception is one fewer name to guess, and `test/wire_names.spec.ts` holds the reference to it: every documented field name, enum value, example key, and query parameter name, each list's sort keys, which must be fields its rows carry, and the sort keys each list route documents, which must be the ones its list takes. It reads what the reference documents, so a value named only in prose, or one the reference leaves out, is the author's to get right. Stored data may keep another form, as the settings blob does, as long as the route maps it to these names.

## Requests

**A read is a GET.** A route that changes nothing is a GET, whatever it answers, so a client, a proxy, or a person can tell from the method alone that it is safe to send, repeat, or prefetch. Describing a post's rendered email is a read, at the preview's own path plus `.json`, beside the page itself. The one exception is a read whose input is a file, which doesn't fit in a URL: planning an import writes nothing, and is a `POST` that takes the list as its body.

**An address goes in the body or the query, never the path.** A path names a resource, and is recorded as that resource's name wherever requests are counted or traced, so a subscriber's address is never part of one: a subscriber is named by its id, and lifting a suppression takes the address in the body. A query string may carry an address, and the lookup by address (`?email=`) and the searches (`?search=`) take one there, since a read has no body. The request URLs Cloudflare records stay in the operator's own account for a few days, visible only to people who can already read the list, and an operator who exports their logs is responsible for what that pipeline keeps. Kestrel's part is what it writes itself, and its log lines cut an address down to its domain (`src/lib/log.ts`).

**A person signs in through any client; a program alone uses a service token.** Once deployed, the access layer issues every admin credential (SPEC §11), and the API has no login of its own. The editor signs in through the browser. Any other client signs in as the person through the access layer's Managed OAuth, which it discovers from the 401 a request with no credential gets: the answer's `WWW-Authenticate` names the protected resource's metadata (RFC 9728), and that names the authorization server. `kestrel login` does this and `kestrel api` sends the access token as `Authorization: Bearer`, so Claude Code needs no flow of its own. A program that runs with no one present sends a service token's two headers instead. The app sees the same signed assertion either way, so a person through Claude Code is the same principal as in the editor, told apart only by the client it names.

**A client names itself.** Every admin request may carry a `Kestrel-Client` header naming the program it came from, in one short lowercase word, its parts joined by hyphens: the editor sends `editor`, and Claude Code `claude-code`. Who made a change is recorded as the person or the service token, from the credential, plus that name (SPEC §11, Who acted), and answered beside it wherever the record is read (`client` on `whoami` and an import's `principal`, `author_client` beside a revision's `author`). A malformed name is a 400 `bad_request` naming the header in `field`, so a typo is never recorded; a well-formed name the server doesn't know is recorded as given; no header means some other program, and answers null. The name grants nothing, since the person could make the same change in the editor: what the server holds Claude to and not the editor, the acknowledgement an import that grows a send needs, holds every request whose name isn't `editor`, so leaving it off never lifts it. A service token's name is ignored, since the token already names the program.

## When the wire changes

The wire changes only in a release, and every change that can break a client is listed under *Breaking* in `CHANGELOG.md`, with what to do in that release's Upgrading paragraph, which gives each renamed route, field, and value old to new. Kestrel's versions look like Semantic Versioning but aren't (`CHANGELOG.md`, `.claude/rules/release.md`): the middle number counts releases and goes up with each one, whether or not it breaks anything, and a patch is fixes only, never a break. So a client author reads the Breaking entries between the version they built against and the one they move to, and never judges compatibility from the number alone.

## Reading and following

A client learns the state of things in two ways.

- **A snapshot** is a plain read: a list, or one resource. A read of sends also returns a `cursor`, the point in the sequence that the read reflects.
- **Following** is one route, the send feed, read from a cursor. It answers with:
  - every send that changed after that cursor, plus every send the clock is setting right now;
  - every open condition across the sends, whether or not it changed, so one read shows every problem;
  - a new cursor, and `more` when changes past it are waiting, to read again at once;
  - the server's `now`, and `read_again_at` by the server's clock.

  The server sets the pace for both clients alike. It is fast while a send can move without anyone acting, and about once a minute otherwise. Reading early is always fine. Reading late loses nothing, because the next read reports everything since the cursor.

A cursor from a database that has since gone back in time, such as after a restore, is refused. The client then takes a fresh snapshot and follows from its cursor.

**Documents come two ways.** The instance's own documentation, the docs and the API reference, is read as data the editor renders, and as Markdown an agent reads: the reference as an index at its own path plus `.md` (the topics every route shares, and every route on one line) and each resource's full reference at `/api/reference/<resource>.md`, so an agent reads the index up front and a resource's reference when its work reaches it, each doc at `/api/docs/<slug>.md`, and each set's index at `/api/docs/<set>.md`. Each is a projection of one source, the docs' Markdown files or the route registration, so the two can't disagree. In a doc's Markdown, a link to another doc points at that doc's Markdown, so an agent can follow it without knowing where the source files live. A page merged into another still answers at its old slug, with the page that now holds its content.

**An agent finds the API from the instance itself.** `/llms.txt` is public, in the llms.txt convention: the publication's name, its public archive and subscribe page, and the Markdown to read first, the reference's index and each set's index of the docs, which take a credential like every route under `/api`: a person's sign-in, or a service token. An agent pointed at nothing but the instance's address reads it there. It is generated from the route registration, each path listed under the access its route has.

## Acting

The client takes an act from the resource's `actions`, so it offers only what the server would accept now. The answer carries the resource as it stands after the act, `changed`, and a new `cursor`, so the client updates its copy without another read. A refused act carries the resource too.

A test send is an act whose outcome is the provider's, not the server's, so the provider not taking it is an answer, never a refusal: `sent: false` with `not_sent`, the provider's own words as `error`, a `message` to show or relay as it stands (what happened, then the fix where it is known, worded as a send's `refused` condition is), and `may_have_arrived` for a provider that never answered. A template test carries one per address it missed.

### Planning, then committing

An act that changes many things at once, on the strength of the publisher's consent, is split in two: a **plan** that says what the act would do and writes nothing, and a **commit** that applies that plan whole or not at all. Importing a list is the one such act (SPEC §7). The plan carries a hash of what the publisher's consent rests on, and the commit names it, so a commit applies the plan the publisher saw or is refused with `plan_stale`. Changes to the data in between that the consent doesn't rest on are applied safely and reported in the answer, not refused. The hash is also the commit's idempotency key: a commit repeated after a lost answer returns the first one's result, marked `replayed`, and applies nothing twice.

What the commit needs from a person is named in the plan and refused by code when missing, as `remake_required` is: an attestation the client shows and the publisher accepts, and each send whose audience the act would grow before that audience is fixed. The plan carries the attestation's words whole, with the name they call the publication by, so a client that words anything around them takes that name from the plan rather than working it out from the settings it read. Claude may give the attestation but never the acknowledgement, which only a person in the editor gives, so an act that would grow a send through Claude, or through any client but the editor, is finished by a person in the editor.

## Refusing

The rows run in the order a request meets them: its credential, then what it sends, then whether what it names exists, then that thing's state, then the deployment. The API reference states each code where it applies, never as one table: a route lists its own, each with its next move from this table, and the Errors topic lists the few any route can give, beside a summary of every status the API answers.

The error body is `{ error, message }`, plus `field` for a refusal about one field of the request, a dotted path for a nested field such as `notifications.to`, or the header's name for a refusal about a request header (`Kestrel-Client`). Every code under Fix the request carries `field` whenever one field is at fault (a body that isn't JSON, or a path, names none), so the reference says so once, in its Errors topic, and a route lists `field` only on another code that carries it (`slug_taken`, `slug_permanent`, `cursor_ahead`). A refusal about a resource's state also carries the resource as it stands, and `retry_after` where waiting is the remedy.

| --- | --- | --- |

| Fix the request | 400, 413, 415, 428 | `bad_request` (with `field`), `subject_required`, `fire_at_too_soon` (a fire time inside the minimum lead, with `field`; the soonest send is Send now, `POST /api/posts/:id/send`), `unsupported_media_type`, `base_required` (a post save without the revision it was based on, with the post as it stands), `slug_invalid` (a slug set by hand that isn't lowercase letters and numbers joined by single hyphens, with `field`), `unrecognized_format` (a file that isn't in the import format at all: convert it), `invalid_field` (a column or value the format doesn't take, with the `row`, the `column`, and the `allowed` values: fix that cell), `too_many_rows` (over this deployment's `limit`: split the file, or raise the limit where the deployment allows), `body_too_large` (413, over a fixed size: split the file) |

A deployment with no Access configured can authenticate no request at all (SPEC §11), so its admin 401 says so: `{ "error": "unauthorized", "reason": "access_not_configured" }`. Signing in again cannot help; setting up Access can. A 401 under a configured Access, and one in local development, carries no `reason`, and the field never says anything else about the request.

While the configuration is refused, every request is answered before any route is matched, so before authentication, and the answer says nothing about the request itself. Under `/api`, at `/health`, and under `/webhooks/`, it is `invalid_config` naming the `variable`. Every other path is one a reader may open, and answers a plain HTML page with status 503 and a `Retry-After` of five minutes, saying it is temporarily unavailable, which names no setting.

A database behind the release is answered the same way, once the configuration is accepted: under `/api`, at `/health`, and under `/webhooks/`, `schema_behind`, as in `{"error":"schema_behind","missing":["0003_post_slug_auto.sql"],"message":"…"}`, and the same 503 page everywhere else. `missing` lists only the release's own migrations, never an instance's own. `message` names them and says what to run. In local development (a dev-shaped server) that is one command, `npx wrangler d1 migrations apply DB --local`. Anywhere else the server can't tell whether it is deployed or a local `wrangler dev` of the deployed settings, since a local server with routes is served under the route's host, so the message names both, `--remote --env production` for the deployed app and `--local --env production` under a local `wrangler dev`. Either way, it adds that an instance runs `npm run sync-migrations` first if the command finds nothing to apply. So `/health` answers `200` only when the configuration is accepted and the database has every migration the release needs.

An error nothing handled answers `500` `internal_error` on the API. On a reader page it answers a plain HTML page saying something went wrong, never a JSON body.

## Adding to the API

1. Start from the spec. If the change alters what a client can rely on, the spec changes first (`.claude/rules/maintainer.md`).
2. Put it on an existing resource and an existing way of reading or acting if it fits (principles 2 and 3).
3. Pass principle 9's questions, and write the one sentence the reference will carry.
4. Register it in `src/app.ts` with its title (the act, as "Schedule a post", which is also its link in the editor's reference, `#/api-reference/schedule-post`, so a reworded title moves the link), a sentence or two of summary and description saying what it does and the rule that is its alone, its body types and fields, query parameters (with `values` when they are a fixed set, which the router then holds them to), what it returns, its own refusals, and one example, so the reference, its OpenAPI document (`GET /api/openapi.json`), and the gate all come from the same entry (principle 10). A route that writes nothing is a `GET`, and one that takes an address never puts it in the path (Requests, above). A resource it returns is named, never described: each object (the send view, a post, a subscriber, and the rest) is described once, field by field, in `src/reference/objects.ts`, a field whose values each have more to say than one line (a condition's kinds) in a table of its own there, and a nested object with a vocabulary of its own (a send's conditions, its halt) as an object of its own, which the holding field names with `object`, and a route lists only the fields it adds beside it. An idea several routes share goes in a concept section (`src/reference/concepts.ts`), not in route prose. Its prose cites no SPEC section or invariant number: the reference's readers (the publisher, the operator, Claude) don't have SPEC.md, so a rule is said in its own words where it applies, and a spec refuses a tag in anything the reference renders. A field's `type` is a short string, written in the forms the OpenAPI document reads as a schema: `string`, `number`, `boolean`, `epoch ms`, a quoted literal, an object's key (`condition`), `[]` for a list, and `|` between alternatives, with `null` as one. A type written any other way still reads in the reference, but it becomes a schema that accepts anything.
5. A new refusal code goes in `src/reference/refusals.ts`, with its status, and in the table above, in the row for the client's next move. A refusal is thrown by its code alone, so a code missing from that registry doesn't compile, and its status is the registry's. Then list it on each route that gives it; a spec refuses a code no route lists unless every route shares it.
6. Update this document only if the change adds a rule or a kind of concept, not a field.
