# Changelog

All notable changes to Kestrel are recorded here.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). A version is `MAJOR.RELEASE.PATCH`, which looks like [Semantic Versioning](https://semver.org/spec/v2.0.0.html) but is not: the major changes rarely, at the maintainer's call; the release counts releases and goes up with each one, whether or not it breaks anything; and a patch is fixes only, never a feature or a break. So a release can carry breaking changes without a new major: they are listed under *Breaking*, with what to do in its *Upgrading* paragraph, and moving from `1.1` to `1.2` means reading them. How an entry is written, and how a release is cut, lives in [`.claude/rules/changelog.md`](.claude/rules/changelog.md).

To move a running instance from one version to another, follow [Upgrade to a new release](docs/guides/07-upgrade.md), which is also served in the editor's Docs tab. Read every entry between your version and the target first.

**Upgrading from 1.13.0.** Two database migrations, which `npm run sync-migrations` brings in: apply them before you deploy with `npx wrangler d1 migrations apply DB --remote --env production` (and `--local` for local development). `0013_who_acted_client` records the client each revision and import came through. No client was recorded before it, and nothing tells a person's change in the editor from one through another program, so every revision and import a person made is read as made in the editor, and those rows are rewritten once, which counts against the day's database writes on Workers Free like any other write; a service token's read as naming no client. `0014_send_acts` adds a record of every act on a send: who scheduled it, moved it, canceled it, or resolved it, and when. It rewrites nothing: a send made before it reads as acted on by no one recorded. Before you deploy, check that your Access application lets people in only through an Allow policy on emails and programs only through a Service Auth policy on a service token: a login through any other kind of policy is now refused, and a search of your Worker's logs for `auth.unidentified` shows any that would be. Run `npm run check-context` in your instance's repository: this release changes the operator's Claude context, and a copy you've edited is merged by hand. To have Claude Code sign in as you, turn on Managed OAuth for the Access application (Lock the dashboard with Access, step 5) and run `npx kestrel login <your instance's address>`; the service token Claude used before can then be revoked, or kept for a script. To let Claude Desktop and claude.ai connect, also add `https://claude.ai/api/mcp/auth_callback` to the Managed OAuth settings' Allowed redirect URIs (the same step); the `api` path already covers the new server.

### Added

- `kestrel login <url>` signs Claude Code in to a deployed instance as you, through Cloudflare Access's Managed OAuth, which you approve in your browser, and `kestrel api <method> <path>` calls the API as you, naming Claude Code as the client, so what Claude changes shows as yours, via Claude Code (SPEC §11). The sign-in is kept in your user config, never in the instance's repository, and renews itself until the Access application's grant session ends; `kestrel logout` forgets it. `kestrel api --local` calls this folder's dev server as its stand-in person, the same way. `--client` names a script of your own instead, and never the editor, which `kestrel api` refuses. A refusal that signing in again can't fix, an Access login that named no one (`access_unidentified`), says what to change in Access instead. It needs Managed OAuth on for the instance's Access application, an optional step the Access guide now covers.
- `kestrel api` describes the API it calls, read from the instance's own OpenAPI document so it matches the release that instance runs: `kestrel api --list [resource]` lists the routes, and `kestrel api help <method> <path>` describes one, its parameters, body fields, answer, and refusals with their next moves. `-f name=value` (a string) and `-F name=value` (typed by the route, or `@file` for a file's text) build a JSON body, or the query string on a GET and for a name the route takes only as a query parameter, and a field the route doesn't take is refused before the request; they can't be combined with `--data` or `--form`. A refusal now also prints its code, message, field, and next move on stderr, the raw body still on stdout. The OpenAPI document names the next move on each refusal any route can give.
- Kestrel records the client each change came through, beside the person or service token who made it (SPEC §11, Who acted). A client names itself on each request in a `Kestrel-Client` header, one short lowercase word (the editor sends `editor`, Claude Code `claude-code`); a malformed name is a 400 naming the header, and a request that names none reads as made through the API. `GET /api/whoami` answers `client`, a revision and a post `author_client`, and an import's record `client` in its `principal`; a service token's is always null. Where the editor names who made a change, a person through another client reads with it, such as "you@example.com via Claude Code" or "you@example.com via the API", and a person in the editor by their address alone. An import that would grow a scheduled send now needs a person in the editor, refused to any other client and to one that names none, as it already was to a service token; the publisher's email about an import still goes only for one a service token commits (SPEC §7, §8).
- Claude Desktop and claude.ai can work with an instance as a custom connector, signed in as you through Cloudflare Access's Managed OAuth, at `https://<your instance>/api/mcp` (SPEC §11). It's an MCP server in the Worker with a short set of tools for publishing in a chat: search and read posts, sends, and subscribers; preview a post's email; save a draft; send a test; schedule, reschedule, or cancel a send; import a list; unsubscribe someone; and `kestrel_api_read` for most other reads, never a write or a bulk export. Each tool acts through the API's own routes, so it's refused as the route is, a refusal coming back to Claude with its next move, and none confirms anything for you: an import's attestation waits for you to accept it in the chat, and an import that would grow a scheduled send is yours to finish in the dashboard. Its calls always name their client `claude`, so what Claude changes shows as yours, "via Claude". The publisher's docs come with it, for Claude to read. Settings, the template, changing a post's archive listing or address once it's scheduled or sent, suppressions, Resolve, uploads, and erasure stay in the dashboard. On connecting, Claude is told to offer a test once a post is scheduled and to send tests only to your test recipients or an address you give as yours. Working with Claude's new "Connect Claude Desktop or claude.ai" section covers adding it.
- `GET /api/posts/:id/preview.json` answers `text`, the email's plain-text part from the same render as the preview, so a client that can't show the page can read what goes out.
- A send records every act on it, a schedule or Send now, a reschedule, a cancel, and a Resolve, with who took it (a person with the client they came through, or a service token by its name) and when (SPEC §6, §11). The send view answers them as `scheduled_by`, `rescheduled_by`, `canceled_by`, and `resolved_by`. The send's page shows them, and the scheduled banner names the latest when it wasn't you in the editor, such as "Scheduled by you@example.com via Claude Code", so a send Claude or automation scheduled never reads as one you scheduled yourself.

### Changed

- The browser tab now names the screen you're on, such as "Subscribers - Kestrel", a post or send by its subject, and a doc by its title, instead of "Kestrel" on every screen, so tabs, bookmarks, and history entries say where they lead. The web version's tab adds "(web version)" after the subject, so it reads apart from the editor's.
- Every admin `401` now carries a `message`, as every other refusal does, and the API reference and OpenAPI document describe its `reason`, which says when signing in again can't help (SPEC §11).
- The scheduled banner is quieter: "No test of this email has been sent yet" is now a muted "Not tested yet" beside Send test email, the button that settles it (SPEC §8).
- A service token now means automation, never Claude: the editor shows its changes as "a service token" (and an import's as "a service token", not "Claude, for you"), the publisher's email about an import a service token commits names the token rather than Claude, and the dashboard says Claude is connected once a post's current revision came through Claude Code. Service tokens keep working as before. The Connect Claude guide is now Connect automation to the API, for scripts, and `/llms.txt` and the API reference point an agent to `kestrel login` first (SPEC §11).
- The operator's Claude context (`template/claude/CLAUDE.md`) has Claude call the API through `kestrel api` instead of curl with a service token's headers, deployed and locally, and run `kestrel login` with the person when they aren't signed in, so Claude's work is recorded as the person's, via Claude Code, rather than a service token's. It also tells Claude never to use a service token in its environment for the person's work, and shows it `kestrel api --list`, `kestrel api help`, and `-f`/`-F`, so it learns a route's body from the instance instead of building JSON by hand. For safety, it also tells Claude never to pass `kestrel api --client`, so a change it makes can't read as made in the editor, where some steps only you may take, and to send a test only to your test recipients or an address you give as yours, asking before any other. It has Claude offer a test once a post is scheduled, since only a test of the scheduled email settles "Not tested yet", and cancel, fix, and schedule again if the test shows a problem. Run `npm run check-context` to bring it in.

### Fixed

- `kestrel login` and `kestrel api` no longer risk losing a sign-in when two commands touch the credentials file at once: every write to it now happens under the lock a refresh holds, a token request gives up after 10 seconds instead of hanging, and a command removes only a lock it still owns.

### Breaking

- A Cloudflare Access login that is neither a person (with an email) nor a service token (with its Client ID) is refused with a `401` whose `reason` is `access_unidentified`, where it was admitted as an anonymous service token with full access. The app accepts only the two kinds of Access policy the setup guide describes, an Allow policy on emails and a Service Auth policy on a service token, so another kind added to the application, such as a certificate or device rule, can no longer grant the admin surface to a caller nobody can name. The editor explains the refusal in place of a sign-in, naming those two kinds and offering Sign out, and each refusal logs `auth.unidentified` with the names of the claims it carried (SPEC §11).
- A commit through the API that would grow a scheduled send's audience is refused `sends_acknowledgement_required` unless it comes through the editor, whoever signed in: a script of yours that commits such an import with your own sign-in now has you finish it in the dashboard, as Claude does (SPEC §7, §11).

## [1.13.0] - 2026-10-19

**Upgrading from 1.12.0.** One database migration, which `npm run sync-migrations` brings in: apply it before you deploy with `npx wrangler d1 migrations apply DB --remote --env production` (and `--local` for local development). `0012_unsubscribe_cause` records why each subscriber left and leaves the suppressions only bounces and blocks. Every unsubscribe before it reads as the reader's own, since the record never said otherwise. Each complaint becomes an unsubscribe by a complaint, and an address it held with no subscriber is recorded as one, unsubscribed and holding only the address. Each erasure's marker becomes a subscriber unsubscribed by an erasure, holding only the address and when, except that someone who signed up again after it stays pending, read as having left by the erasure until they confirm. An erasure that found a bounce or a block already on an address left no trace of itself, so that address keeps its suppression alone. It rebuilds the subscribers and suppressions tables, copying every row once, which counts against the day's database writes on Workers Free like any other write. Deploy straight after applying it: until this release is serving, the previous one fails to record a reader's unsubscribe, a confirmation from someone who once left, an erasure, and a complaint report, which the new tables refuse. SES retries a refused report, so complaints arrive once the deploy lands; a reader whose unsubscribe failed meanwhile has to unsubscribe again. Run `npm run check-context` in your instance's repository: this release changes the operator's Claude context, and a copy you've edited is merged by hand. Several API changes can break a script of yours, each listed under Breaking; the table gives every renamed route, field, value, and sort key, old to new. A request that still sends an old name is refused with a 400 naming it, never answered as if it had been read: every API route now refuses a body field, a query parameter, or a filter value it doesn't take, so check a script's requests against the API reference before you deploy.

### Breaking

- One naming rule on the wire: every JSON field and enum value is snake_case, and a list's sort key is the name of the field it sorts by. The settings (its preferences, its deploy reflection, `in_use`, and `notification_status`), the build info, `whoami`'s token id, the dev routes' `run_id` and the dev outbox's `provider_id` and `sent_at`, the `backing_off` and `needs_attention` phases, and the sort keys of posts, sends, subscribers, and deliveries take their new names; the stored settings keep theirs, so no migration runs. The Upgrading paragraph lists every rename.
- An import's outcomes are renamed into one form, the past tense of what the import does to the address, and none says "blocked" any more, which in the editor and the API means only your own block: `create_confirmed` is now `added_confirmed`, `confirm_pending` is `confirmed_pending`, `mark_unsubscribed` is `unsubscribed`, `create_unsubscribed` is `added_unsubscribed`, `blocked_by_suppression` is `kept_suppressed`, and `suppression_added` (as an outcome, not the row's field of that name) is `suppressed`. They change in an import plan's and a commit's `counts`, `rows`, and `differed`, the format route's `outcomes`, and an import's record, where one committed before this release reads under the new names too. A script that matched an old name matches the new one (SPEC §7).
- A send's per-recipient buckets have one vocabulary, the statuses and events its delivery rows store: `counts.in_flight` is now `counts.dispatched`, and `outcomes.in_flight` and the deliveries' `view=in_flight`, which meant pending and dispatched together, are split into `pending` and `dispatched`, so one name never counts two things. A delivery row's `status`, `event`, and `bounce_kind` are now typed to their values (SPEC §12).
- A post reads the same on every route and refers to its send by one fixed reference, `send`: `{ id, status, fire_at, rev }` of its active send, else the one that sent it, or null, with the whole send one read away at `GET /api/sends/:id` and `rev` saying whether a copy of it is current. It carries `actions` too, what the server would take for it now (`edit`, `delete`, and, while an email provider is connected, `schedule` and `send_now`). They replace a list row's `fire_at`, `active_send_id`, and `active_send_status` and one post's `scheduled`, `sending`, and `sent`, and its `author` moves inside the post. The editor offers a post's controls from its `actions`. The posts list's `fire_at` sort is now `send.fire_at`.
- A subscriber carries its suppression inside it on every route, `suppression: { reason, detail, created_at }` or null, in place of `suppressed`, `suppression_reason`, and `suppression_detail`, which sat in list rows only, and `suppressed` beside one subscriber's answer.
- A refusal about a resource's state carries it as it stands: `post_not_draft` and `slug_permanent` the `post`, `settings_changed` and `conflict` the `settings`, an erasure's `run_in_progress` and an Add's `signup_required` the `subscriber`, `suppression_changed` the `suppression`, and every send refusal the `cursor` beside the `send`. The re-make's `sends`, `in_use.sends`, and `remade` are full send views, in place of a smaller reference.
- `DELETE /api/suppressions/:email` is replaced by `POST /api/suppressions/lift`, which takes `{ email, reason }` in the body, so a subscriber's address is no longer in a logged path, and lifts only the reason named: a different one standing now is refused with `suppression_changed`, carrying it. It lifts a block (`manual`) or a bounce (`bounce`, `import_bounce`), the only reasons a suppression has now; any other is a 400. It answers `{ email, lifted }` in place of `{ email, cleared }`. The old route answers 404.
- Each mark on an address has one owner (SPEC §7). The consent state is the person's and now keeps why they left, as a subscriber's `unsubscribe_cause`: `reader` (their link or one-click), `publisher` (Unsubscribe on request), `complaint`, `erased`, or `import` (a list that says they left, not why). When someone who left leaves again, the stronger cause stands: an erasure, then a complaint, then the first. The suppression is only the sender's side, so its `reason` is `bounce`, `import_bounce`, or `manual`, and `complaint`, `import_complaint`, and `erased` are gone from it: a complaint and an erasure are unsubscribes with that cause. A script that read a complaint or an erasure from a suppression reads the subscriber's `unsubscribe_cause`.
- Adding an address that left by a complaint or an erasure (`POST /api/subscribers`) is refused with 409 `signup_required`, carrying the `subscriber`, and sends nothing: only the person's own sign-up through the subscribe form brings them back. `acknowledge_erasure` and `erasure_acknowledgement_required` are gone, and so is `erasure_marker` on a lift. Adding anyone else who left sends a confirmation, as before (SPEC §7).
- Erasing a subscriber (`POST /api/subscribers/:id/erase`) answers `{ subscriber, deliveries }`, the subscriber as the erasure left them, in place of `{ erased: { email, deliveries, suppression } }`. A repeat answers the same subscriber with `deliveries: 0`, where it answered 404. An erased subscriber's `unsub_token`, `origin`, and `opt_in` are null, so a script that reads them handles null (SPEC §7).
- The import format is `kestrel-subscribers/2`, which the export now writes: an `unsubscribed` row says why the person left in `unsubscribe_cause` (`reader`, `publisher`, `complaint`, or `erased`), a row that doesn't say is recorded as having left elsewhere, and `suppression` takes only `bounce` or `manual`. A version 1 file still reads, its `complaint` or `erased` suppression read as an unsubscribed row with that cause, whatever its status, and a row naming no version may use either version's values. An erasure is recorded with the address alone. A row that erases someone already on the list does what **Erase** does, past sends' records included, and plans as a new outcome, `erased`, so a script that sums outcomes adds it; the commit answers 409 `run_in_progress` while a send is handing such a person to the provider. A cause on a row that isn't `unsubscribed` is refused with `invalid_field` (SPEC §7).
- An import plan's `daily_writes_warning` is now `workers_plan_advice`, and means something else: on the Workers Free plan's limits, the advice to move to Workers Paid when the import would leave more than 1,000 confirmed subscribers, rather than a count of the day's database writes. A script that read the old field reads the new one (SPEC §7).
- `GET /api/suppressions` pages like the other lists: it answers 50 suppressions at a time with `page`, takes `limit`, `offset`, `sort` (`created_at`, `email`, or `reason`), and `dir`, and filters by `reason` and an email contains-search (`search`). It answered up to 1,000 at once and silently left out any past them, which a list imported from another provider can reach on its first day. A script that read the whole list in one call follows `page` (SPEC §7).
- Every API route takes only what the API reference lists for it: a body field it doesn't name, a query parameter it doesn't list, or a value outside the ones a filter takes is refused with a 400 naming it in `field`, where most routes ignored it and answered as if it had been read. `GET /api/posts?status=bogus` listed every post and `GET /api/subscribers?suppressed=maybe` the whole list; both are now refused, and so is a parameter given twice, a `seed` or `size` the dev seed can't read, and a `kind` other than `human` or `service` on the dev token. A reader page, such as an archive link carrying a tracking parameter, still takes what it is sent.
- Describing a post's rendered email (where its preview is, its `subject`, `warnings`, and `frozen`) writes nothing, so it is a read: `POST /api/posts/:id/preview` is now `GET /api/posts/:id/preview.json`, with the same answer, and a `POST` to the old path is a 404. The rendered page itself stays at `GET /api/posts/:id/preview`.

### Added

- Each subscriber has a page of their own, opened from their row, their address, or **View subscriber** in the row's menu, in place of the View subscriber dialog and the list's How they joined column, which moves to it. It answers "did they get my post?": a line under the address says whether they receive your posts and, if not, why, then every send their address was in, newest first, with what the provider did and reported, each linking to its record. It also shows how they joined, with the import that brought them (its file, when and by whom, and the attestation's version), their suppression with the provider's or your words and since when, why they left (for a complaint, which send it was about), and the row menu's acts. The API adds `GET /api/subscribers/:id/deliveries`, a page at a time, `GET /api/imports/:id`, and `receives_posts` on every subscriber (SPEC §7, §8).
- Each instance serves its API as an OpenAPI 3.1 document at `GET /api/openapi.json`, behind Access like the reference, so a client generator or an API client such as Postman can import it. It is generated from the same registration as the reference, so it lists the same routes, objects, and refusals, and `/llms.txt` and the reference's index name it.
- Each instance serves a public `/llms.txt`, so an agent given only its address learns what it is and where to start: the publication's name, its archive and subscribe page, and the API reference and docs behind Access, with a link to Connect Claude to the API for a service token. It is generated from the routes the instance registers, so it always matches the release (SPEC §11).
- A scheduled post that no test has been sent for says so on the editor's scheduled banner until the first test lands, and the API carries it as an `untested` condition (`info`) on the send and in the feed, so Claude can tell whether the email was tested (SPEC §8).
- **Clear** in a subscriber's ⋯ menu lifts a bounce, after a dialog that says the address failed and to clear it only when you know its cause is gone, which before only the API could do (SPEC §7). The list's legend, under What you can do, and the API reference say when to use it and when to use **Unblock**, in the same words.
- The operator's Claude context lifts a suppression through `POST /api/suppressions/lift`, naming the reason it shows, and lifts only a block or a bounce. `npm run check-context` offers the change to an existing instance.

### Changed

- A reader who marks a post as spam is unsubscribed by it, as their own link would, instead of suppressed while still confirmed, and comes back only by subscribing again themselves. Every complaint does, whichever email it is about, a confirmation email included; one that reaches no subscriber changes nothing. Each is logged as `subscriber.complained` (SPEC §7, §12).

## [1.1.0] - 2026-09-24

**Upgrading from 1.0.0.** This is a minor release that carries breaking changes to the sends API (see *Breaking*): no instance of 1.0.0 was deployed, so the version stays in the 1.x line rather than moving to 2.0.0. It adds one database migration: run `npm run migrate:remote -- --env <name>` before deploying. Update any script or agent prompt that reads sends. For local development, run `npm run migrate:local`; a local database that ran a pre-release build's migrations is rebuilt instead: stop `wrangler dev`, delete `.wrangler/state/v3/d1`, and run `npm run migrate:local`.

### Breaking

- Every sends route now carries a send as one shape, the send's view: `GET /sends` rows, `GET /sends/:id`'s `send`, each feed item, and the answer of schedule, Send now, cancel, reschedule, and Resolve. It holds `status`, the times, `rev`, `as_of`, `audience` (`count`, and whether it is `fixed` at fire), `counts`, `dispatch`, `delivery`, `provider` (with `halt`), `phase`, `conditions`, `actions`, `next_change_at`, and `links`, in place of the flat `c_*` and `halt_*` columns, `recipient_count`, `audience_resolved_at`, the separate `progress` (`state`, `total`), and the raw row. Every action answers `{send, cursor}`, and `GET /sends/:id` answers `{send, outcomes, cursor}`, with the archive link at `send.links.archive` instead of `archive_url`, `published`, and `slug` (SPEC §8).
- `GET /sends/:id/progress` is gone: read `GET /sends/:id`, which answers 304 to `If-None-Match` while the send is unchanged, or follow the feed.
- A send's frozen email is no longer carried on the send (`rendered_html`, `rendered_text`): read it at `GET /sends/:id/email?format=html` or `format=text`.
- Sends report what is wrong with them as `conditions` and what can be done as `actions`, in place of `attention` and `stuck`, on every send's view. Each condition (`missed`, `stuck`, `wedged`, `refused`, `provider_unavailable`, `bounce_spike`, `remade`) carries a severity, when it began, the server's own words, and the action that settles it, if any; `actions` lists exactly the cancel, reschedule, or Resolve the server would take now (SPEC §8).
- A scheduled send can no longer be canceled or rescheduled once its fire time has passed, even before the sweep starts it: the review window closes at the fire time (SPEC §6), and the API answers 409 `window_closed`.
- Scheduling, Send now, cancel, reschedule, and Resolve refuse with a code per reason (`window_closed`, `send_canceled`, `post_not_draft`, `active_send_exists`, `subject_required`, `fire_at_too_soon`, `settings_changed`, `not_wedged`, `run_in_progress`, `count_changed`, `precondition_failed`) instead of `conflict` or `bad_request`, each carrying the send as it stands where there is one.
- Canceling a send that is already canceled answers 200 with `changed: false` instead of a 409, and a reschedule to the time a send already has answers the same way, so a retried request is safe.
- Resolve now works only on a wedged send, and answers 409 `not_wedged` otherwise; before, it could settle ambiguous recipients while others were still waiting to be handed off.
- Every list (`GET /sends`, `/posts`, `/subscribers`, `/sends/:id/deliveries`) refuses a `sort` or `dir` it does not list, or a `limit` or `offset` that is not a whole number, with a 400 naming the field, and `GET /sends` does the same for an unknown `status` or `failures`, instead of quietly reading them as the default.
- `GET /sends/:id/deliveries` now refuses an unknown `view` with a 400 naming the field, instead of quietly showing failures.
- A provider halt's `since` and `retry_at` (under `provider.halt` on a send) are null when the record lacks them, instead of reading as the moment of the request.

### Added

- `GET /sends/feed?since=<cursor>` reports every send that changed since a read of sends, whichever client changed it and whether a write or the clock did (turned due, missed, in flight too long, wedged), each with its phase, counts, and any problem, plus a new cursor and `read_again_at`, when to read again; without `since` it lists the sends that can change on their own. `GET /sends/:id` now carries a `cursor` too, so a client can follow one send from its own read without polling it. A cursor reads `<seq>.<at>` (the change sequence and the server's time at the read), a documented format, so a client holding cursors from several reads can compare them and follow everything from the earliest in one read (SPEC §8).
- `GET /sends` rows carry a `rev` that rises with every change a reader could see of the send, ordered across all sends, and the response carries a `cursor` marking where the read stood (SPEC §8).
- `GET /posts` now carries a `cursor`, where the read stood among the changes to sends, so a client listing posts can follow their sends with `GET /sends/feed` from the same read (SPEC §8).
- `GET /sends/feed` now reports a send deleted with its post under `removed`, so a client drops it instead of keeping a row for a send that is gone (SPEC §8); takes `limit` (default 100, at most 500), and says `more` when a read stopped short, to be read again at once; and gives each send a `next_change_at`, the earliest it can change with no one acting.
- Each `GET /sends/feed` read now lists every open condition across the sends, whether or not they changed, so one read shows every problem.
- `GET /sends/feed` answers a cursor ahead of the database (after a local reset or a restore) with a 409 `cursor_ahead`, and the dashboard and the Sent list then read their sends again, where before such a cursor silently reported nothing ever again.
- Cancel, reschedule, and Resolve take `If-Match: "<rev>"` and refuse with a 412 if the send has changed since the caller read it; Resolve also takes `expected_count`, refused if the number of ambiguous recipients has moved; and cancel and reschedule answers say whether anything `changed`.
- The bounce-spike warning is now worked out by the server and reported on the send, so Claude sees it as the dashboard does, and a re-made scheduled send reports `remade` until a test of its re-made email is sent.
- `MIN_LEAD_SECONDS` sets the minimum lead, how long every send stays cancelable before it fires, per deployment: five minutes when unset, never under one minute in any environment, and never over a day (a value outside that stops the app with an error naming it). Settings shows it read-only, the editor's Schedule, Send now, and Reschedule use it instead of a fixed five minutes, and the API reference states it on the routes that enforce it (SPEC §6). Local dev ships with it at one minute; add `MIN_LEAD_SECONDS="60"` from `.dev.vars.example` to an existing `.dev.vars`.
- `npm run simulate-send -- --in 90s` schedules a demo send on the local dev server through the API (loading the demo first if the database is empty) and prints the link to watch it; it refuses a time inside the minimum lead and says why.
- Local development can model Amazon SES or Resend: `SIMULATE_SENDS` takes `resend`, `ses`, or `1` (the generic simulation), optionally with `:none` for a run with no failures, and Settings names the provider modeled. The SES profile reaches a wedged send and Resolve, and a spent daily quota with its spaced-out retries (SPEC §10). `GET /api/settings` reflects the simulation under `deployment.simulation`.

### Added

- Markdown authoring with a single render path shared by preview, test, schedule, and send, so a clean test proves exactly what ships.
- Scheduling behind a cancelable review window: the render is frozen and the post soft-locked when scheduled, and stays cancelable until it fires. "Send now" runs the same path after a short cancelable buffer.
- Batched, idempotent delivery: a retry or restart never re-mails a recipient the provider already accepted.
- A double opt-in subscriber list the app owns end to end: consent, one-click unsubscribe, and suppression from bounces and complaints via provider webhooks.
- A permanent per-post public archive (view-in-browser), self-contained on the app's own origin, with an optional archive-on-your-apex enhancement.
- A public reader surface: landing page, archive index, and subscribe / confirm / unsubscribe.
- An admin editor and authoring API behind Cloudflare Access (human SSO plus a service token for Claude), with a local dev token for local-only development.
- Configurable publication identity (name, tagline, logo), email template, and confirmation-email wording, plus default test recipients. Preferences only, never secrets.
- A swappable email-provider seam with a fake in-memory transport for local dev and tests, alongside SES and Resend adapters.
- An in-app reference room: the setup guide and the API reference, served read-only inside the editor.
- A build-version stamp: every instance reports its version, commit, and build time, read-only in the editor and at `GET /api/version`.
- This changelog and a semantic-versioning release process.
