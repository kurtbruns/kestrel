# Changelog

All notable changes to Kestrel are recorded here.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). A version is `MAJOR.RELEASE.PATCH`, which looks like [Semantic Versioning](https://semver.org/spec/v2.0.0.html) but is not: the major changes rarely, at the maintainer's call; the release counts releases and goes up with each one, whether or not it breaks anything; and a patch is fixes only, never a feature or a break. So a release can carry breaking changes without a new major: they are listed under *Breaking*, with what to do in its *Upgrading* paragraph, and moving from `1.1` to `1.2` means reading them. How an entry is written, and how a release is cut, lives in [`.claude/rules/changelog.md`](.claude/rules/changelog.md).

To move a running instance from one version to another, follow [Upgrade to a new release](docs/guides/07-upgrade.md), which is also served in the editor's Docs tab. Read every entry between your version and the target first.

**Upgrading from 1.7.0.** If your `production` block sets `PROVIDER` to `fake` on a real hostname, this release refuses it: set your email provider, or make it `""` until you [connect one](docs/get-started/04-resend.md). A hosted demo that runs `fake` on a real hostname on purpose adds `ALLOW_FAKE_PROVIDER: "true"` before it upgrades, to the env it hands Kestrel: its `vars`, or the object it builds if it builds one, and that object's type. If your `production` block has no `PROVIDER` line, you may add `"PROVIDER": ""` to its `vars` to quiet wrangler's warning that it's missing there; it means the same as leaving it out.

### Breaking

- `PROVIDER` set to `fake` is now refused unless `APP_ORIGIN` is on `localhost` or `127.0.0.1`, naming `PROVIDER`, so the development value copied into production, which wrangler's warning about a var missing from `production` invites, shows at Deploy's check instead of opening signups whose confirmations go nowhere and recording sends no one receives. A hosted demo that runs `fake` on purpose opts in with `ALLOW_FAKE_PROVIDER` set to `true`, which no other provider reads (SPEC §9).

### Added

- Local development can run as a deployment with no email provider connected: `SIMULATE_SENDS=not-connected` refuses every send, closes signups, and holds a due send, which goes out at its next retry once the switch is off, with local sign-in still on, so the editor's not-connected state can be seen without deploying. A deployed instance ignores it (SPEC §10).
- While no email provider is connected, the editor says so where sending would otherwise look possible: a draft's page notes it can be written and previewed but not sent, and a scheduled send's dashboard card and editor banner say it will be held when it fires. `kestrel dev` prints a line naming what `SIMULATE_SENDS` makes of the run, `not-connected` or a simulated provider, since wrangler shows the variable only as "(hidden)".

### Changed

- A new instance's `production` settings declare `"PROVIDER": ""`, which means no provider connected, so wrangler no longer warns on every production command that `PROVIDER` is missing there. Connect an email provider, and the SES guide's switch step, now say to change it rather than add it.
- The operator's Claude context (`.claude/CLAUDE.md` in a new instance) carries a new safety caution: `PROVIDER` stays empty in production until the provider step and is never `fake`, whatever a wrangler warning suggests, so an instance's Claude doesn't "fix" the warning by copying the development value into production. An instance made before this release can merge the line by hand.
- Deploy the app's step 3 creates the database and the image bucket with `--env production --binding … --update-config`, so Wrangler writes the new database's id into the `production` block itself, with no id to copy and no prompt to decline. The prompt's default, Yes, added a second binding to the production database in the development settings.
- A new instance installs `@types/node` as a dev dependency, so `npm run typecheck` no longer ends with Wrangler's "Action required: Install @types/node". The Node types stay out of the type check, so the Worker's own types still apply. An existing instance can silence the notice with `npm i -D @types/node`.
- The operator's Claude context now names `--env production` on every Wrangler command that creates or binds a resource, not only deploying and migrating, since without it Wrangler offers to bind the new resource in the development settings. It bears on safety: it keeps a binding to a production resource out of the development settings. `npm run check-context` reports the change; if you edited your `.claude/CLAUDE.md`, replace that line by hand.
- A send held because no email provider is connected reads once on the dashboard and the Sent page, one red message with the not-connected state instead of two, and its advice, there and on the send's page, links to Connect an email provider and says "then deploy" rather than "then deploy again". In the local not-connected preview it says to restart `npm run dev` without `SIMULATE_SENDS=not-connected`, which the settings API now reports as `deployment.notConnectedPreview`.

### Fixed

- An `ACCESS_TEAM_DOMAIN` stored with `https://` or a trailing slash no longer fails every sign-in with a `401` that says nothing of why: the app reads it as the bare hostname. A value that still isn't a hostname, such as one with a path or a port, is refused, naming `ACCESS_TEAM_DOMAIN`, like any other setting the app can't run on (SPEC §9).
- The **Use Amazon SES instead of Resend** guide now says which provider switch can mail someone twice: moving to SES leaves an unanswered request's recipients for Resolve, while moving to Resend, from SES or another Resend account, can deliver the post to them again. It also shows the `production` vars as they end up, so `AWS_REGION` isn't pasted twice, puts Access covering the SES webhook first among the reasons a subscription stays pending, and gives the IAM user, configuration set, and SNS topic distinct names.
- Before Access is set up, the deployed editor says it is locked until you set up Access, with a link to the guide, instead of saying your session expired; the API's 401 carries `reason: "access_not_configured"` in that state.
- A dialog or row-action menu no longer stays open over the next page after you navigate away, such as Add subscriber after pressing Back, where its confirm could act on something no longer on screen. Leaving a page closes what it opened; a write already started from a dialog still completes, and a template or identity save left waiting on its confirmation says it wasn't saved.
- `/health` no longer answers ok on a database that hasn't run every migration the release ships, as after a skipped Apply the schema step or a deploy made before its migration. It answers `500` `schema_behind` naming the missing migrations and the command that applies them, the editor says the same in place of the app, the public pages say the newsletter is temporarily unavailable, and nothing is sent until they're applied; your own `local_` migrations don't count. An error nothing handled on a public page now shows a plain error page rather than a raw JSON body (SPEC §5, §9).

## [1.7.0] - 2026-10-12

**Upgrading from 1.6.0.** If your `production` block in `wrangler.jsonc` sets `PROVIDER` to `resend` or `ses`, nothing changes. If it still sets `fake` (as Get started's Deploy step set it until you connected a provider), delete that line before you deploy, so the instance runs with no provider connected rather than recording sends it never delivers, and [connect an email provider](docs/get-started/04-resend.md) when you're ready. If it sets no `PROVIDER` at all, the instance used to run on `fake` and now refuses to send; connect a provider first if it has readers. A send already scheduled on such an instance is held, with no one marked sent, until a provider is connected; it then goes out at its first retry after that, which may be long after its fire time, and it can't be canceled meanwhile, since it is already sending. A local development config that leaves `PROVIDER` unset needs `"PROVIDER": "fake"` in its top-level `vars`, as a new instance's has. If only one of the `ACCESS_TEAM_DOMAIN` and `ACCESS_AUD` secrets is stored (`npx wrangler secret list --env production` shows which), store the other before you deploy: this release refuses that configuration, and until both are stored its public pages say the newsletter is temporarily unavailable and nothing is sent. If any of `APP_ORIGIN`, `ARCHIVE_ORIGIN`, `MEDIA_PUBLIC_BASE`, `SENDING_DOMAIN`, or `FROM_ADDRESS` in your `production` block is still on `example.com` (the template's placeholder), replace it with your own before you deploy, whatever `PROVIDER` says: this release refuses it on every provider but `fake`, and until it's fixed the public pages say the newsletter is temporarily unavailable.

### Breaking

- An unset `PROVIDER` now means no email provider is connected, not the `fake` stand-in. Such a deployment runs, and refuses everything that would send with a 409 `provider_not_connected`: scheduling, send now, a test email, a test notification through the provider, and adding a subscriber; its public subscribe page says signups aren't open yet instead of taking an address it can't confirm. A send scheduled before is held, consuming no one, as a `refused` condition with the new cause `not_connected` and advice to connect a provider. `fake` now runs only where it is named, as local development and a demo do, and a new instance's production settings ship without `PROVIDER` until Get started's Connect an email provider step sets it (SPEC §9).
- A deployment with no email provider connected is now refused while any origin or sending setting is still on the template's `example.com` placeholder, as one with a real provider already was, so a missed edit shows at Deploy's check instead of at the provider step. Only `fake` may keep the example names (SPEC §9).
- A deployment with only one of `ACCESS_TEAM_DOMAIN` and `ACCESS_AUD` stored is now refused, naming the one that's missing, like any other configuration the app can't run on: its public pages say the newsletter is temporarily unavailable, and nothing is sent, until the other is stored. It used to keep serving readers and sending while the editor and Claude were locked out without saying why (SPEC §9).

### Added

- Reader pages, post pages included, show the publication's logo as the browser tab's icon when one is set; with no logo, the browser's default icon stays (SPEC §5).
- A setup guide, **Try Kestrel locally first**, runs a new instance locally with the demo publication, with no Cloudflare account or Git host, and shows how the folder becomes your instance's repository when you deploy.

### Changed

- A new instance's `.dev.vars.example` holds only what local development uses (the local sign-in secret, the minimum lead, and the send simulation). The blank Access and email-provider entries are gone: they did nothing locally, and setting an Access value there turned local sign-in off. A deployed instance's secrets are listed in the Configuration reference.
- The setup guide's Overview page is folded into Deploy the app: what Get started needs is now Deploy's Before you begin, followed by choosing your hostnames. Get started is five steps, and Connect Resend, now step 3, is renamed Connect an email provider: it still walks through Resend, and points to the SES guide.
- While the configuration is refused, the public pages readers see answer a plain "temporarily unavailable" page (503) that names no setting, instead of the JSON error naming it; the API, `/health`, and the webhooks still answer `invalid_config` with the variable. The editor shows one page saying what's wrong, with a link to that setting in the Configuration reference, instead of failing call by call (SPEC §9).
- `auth.mode` in `/api/whoami`, and `authMode` in the Settings deployment reflection, now say how the request signed in (through Access, or with the local dev token), rather than whether Access is configured.
- The dashboard's first-run checklist orders its steps by what each needs first: name the publication, connect a provider (or confirm the sending domain), write the first post, then share the subscribe link. Writing used to come second, and starting a draft ends the checklist, so the steps after it were lost.
- While no email provider is connected, the editor says so wherever a send would be refused, each time with a "Connect an email provider" link to the setup step: the dashboard's health block and the Sent page carry an amber warning that nothing can be sent yet, the first-run checklist asks you to connect a provider in place of confirming the sending domain and says signups open once one is, Settings' Email provider row reads "No email provider connected" and its Ways to subscribe says signups aren't open yet, and the Send-a-test, Schedule, and Add subscriber dialogs say so in amber before you commit, with their act disabled and nothing to fill in (no recipients, time picker, Send now, or address), until a provider is set. A send held for want of a provider says no provider is connected, on its page, in the dashboard's attention line, and in the notification, rather than that the provider is refusing the account. Local development keeps its "nothing is delivered" wording.

## [1.6.0] - 2026-10-11

**Upgrading from 1.5.0.** One database migration: run `npm run sync-migrations`, then `npx wrangler d1 migrations apply DB --remote --env production` (and `--local` for local development) before deploying. Existing posts keep their slugs and read as set by hand; tick *Auto-generate from subject* on a draft to have its slug follow the subject again. On npm 12, to end `npm install` without the blocked-install-scripts warning, add this to your `package.json` (a new instance has it already): `"allowScripts": { "esbuild": true, "fsevents": true, "workerd": true }`.

### Breaking

- Cancel, reschedule, and Resolve no longer take a precondition: an `If-Match` header on them, and Resolve's `expected_count`, are now ignored, and the `precondition_failed` and `count_changed` refusals are gone. Each act applies to the send as it stands and answers with the result, so a retry after a lost answer is answered `changed: false` instead of a 412, and two acts made moments apart both land, each shown at once and reversible before the fire time (SPEC §1, §8).

### Added

- Settings has a **Reader pages** section that shows every page a reader can land on, including the expired and invalid links a reader rarely meets and the landing page and archive as visitors find them before your first post: an outline lists each journey (subscribe, confirm, unsubscribe, reading) with its pages, and the one you pick shows beside it at desktop or phone width. Each is the real page rendered with your publication's identity and sample values, so you can see what readers see without walking the flows; nothing on a preview acts (SPEC §5).
- The editor shows a post's **web version**: the post as its public page will look, with the template's email-only parts left out and the masthead and display font added, so you can proof the page before it's permanent. **Web version ↗** in the editor opens it in a new tab, under a strip above the page that says where the post stands and where its public page will be, and replaces **Open in browser**, which showed the same email as the Preview tab. The email's own "View in browser" link in the Preview tab opens the web version too, rather than a public page that doesn't exist yet. Once a post's send starts, the web version opens its public page (SPEC §5).

### Changed

- A logo you upload in Settings is now cropped to its center square and saved as a 256 × 256 image, so it looks the same everywhere and is never stretched in an email. The tile shows the result, the confirmation says when the edges were cropped, and Replace picks another. A logo you uploaded before that isn't square is flagged in Settings, since emails show it stretched; upload it again to have it cropped.
- Settings orders its sections by whom they serve, editable first: your publication's identity; then, in the order a reader meets them, the ways to subscribe, the confirmation email, and the reader pages; then the email template and your test recipients; then notifications; and last, read-only, what only a redeploy changes (the email sender and the instance). The embeddable form's Styled | Plain choice is now the same toggle as the page's other two-way choices.
- The subscribe page and the Styled embed tell a reader what happens next in plain words, "We'll email you a link to confirm. Unsubscribe anytime.", instead of "Double opt-in".
- Settings' **Ways to subscribe** shows its two ways as matching parts of one card, the subscribe page first and the embeddable form second, each with a line on what it is for. The page's address reads as a value with Copy and Open beside it, and the embeddable form shows beside its snippet, both in view at once, with the Styled | Plain choice named only on its toggle and a **Copy HTML** button at the end, where the form's one act belongs. The **Styled** snippet, now offered first, looks like your hosted subscribe page: a Georgia serif headline over a sans body, in the reader pages' ink colors. A form already pasted into a site keeps the look it was copied with; copy it again to take the new one.
- Copying in the editor says it worked on the Copy itself, its glyph turning to a check for a moment, instead of a "Copied" toast: the subscribe page's address and the embeddable form in Settings, the addresses and setup step on the dashboard, and the whole template on the Template page.
- A post now records whether its slug follows the subject or was set by hand (`slug_auto` on the post and on a save), which the editor's *Auto-generate from subject* box now shows rather than guesses. A slug that follows is derived and numbered afresh on every draft save, through the API as well as the editor, so a script that creates posts should take the slug from each save's answer rather than keep the one it was created with. A draft numbered because another post held its slug (`spring-update-2`) drops the number once that post is deleted, and a slug set by hand that looks numbered, like `spring-update-2027`, is no longer mistaken for one that follows and replaced by a subject edit (SPEC §4).
- A post's page, the archive index, and the landing page show a post as soon as its send starts, dated by when it went out, so a reader who opens "View in browser" while a large send is still going out finds the post instead of "Not found". A send's view links the published post from the start too (SPEC §5).
- The confirm, unsubscribe, and post-not-found pages now wear your publication's reader look (its name, logo, and serif headline), like the subscribe page, instead of a plain grey card, so a reader arriving from an email sees your newsletter, and the pages that ask a reader to confirm or to unsubscribe name it in their headline when it has a name ("Confirm your subscription to …", "Unsubscribe from …?"). They carry no subscribe call to action in the masthead, and they are never cached or indexed, since some show the reader's address (SPEC §5).
- A test email's links now land on pages that say what they are. Its "View in browser" link, before the send starts, opens "Nothing here yet" (the same page any archive address without a published post shows, so a scheduled post is never revealed) instead of "Not found", and its unsubscribe link, like the one in the editor's preview, opens the page a subscriber sees instead of "This link is invalid": marked as a test, with a sample address, and walking through it changes no one's subscription (SPEC §5, §7).
- The operator's Claude context no longer tells Claude to send `If-Match` when it acts on a send, or to handle `precondition_failed`, since neither applies any more. It now says an act is safe to repeat and that every answer carries the send as it now stands. `npm run check-context` reports the change; if you edited your `.claude/CLAUDE.md`, replace that line by hand.
- `kestrel seed` and `kestrel reset` (`npm run seed`, `npm run reset`) with no port given now act only on the dev server `kestrel dev` started in the same folder, and refuse otherwise: when none is running there, or when the server on its port isn't that one (started some other way, or another folder's). Before, they fell back to port 8787 and could wipe another local server's database. `PORT` no longer aims them, since a shell can carry it unawares; to act on another server on purpose, name its port as an argument: `npm run seed -- 8787`.
- The operator's Claude context now says that seed and reset act only on the dev server started in the instance's folder, and tells Claude to start that server when they refuse rather than name another server's port, which the person must mean. It bears on safety: both wipe the database they reach. `npm run check-context` reports the change; if you edited your `.claude/CLAUDE.md`, add the sentence by hand.

### Fixed

- An email you've sent, and its archive page, now keep the logo it went out with. Before, uploading a new logo changed it in every past email and archive page beside their original name and tagline, and removing the logo left a broken image in all of them. Each upload is now kept, and a new one or a removal changes only what you send from then on. A logo uploaded before this release stays where its past emails point, and from now on is never replaced (SPEC §9).
- A publication with no name, and no display name on its sending address, is no longer called "Newsletter" on its reader pages while its email carries no name. Every surface now reads the name the same way and, with none, shows none: the pages say "Subscribe", "Confirm your subscription", and "Unsubscribe?", their tab titles drop the name, the masthead shows only what you've set (or a link home reading "Archive"), and the subscribe embed in Settings reads "Subscribe" (SPEC §9).
- Toasts no longer pile up in a column up the middle of the screen. At most three show at once, a repeated message (clicking Copy five times, or a save failing again while you type) restarts the one already showing instead of adding another, and one leaving lets the rest slide into place. A longer toast on a phone now uses the screen's width instead of wrapping into a narrow column.
- A new instance's `npm install` on npm 12 no longer ends with a warning that install scripts were blocked for esbuild and workerd (and fsevents on a Mac). The instance's `package.json` now allows them by name, so their scripts run as wrangler expects and the entry doesn't go stale when wrangler moves to a new version.
- Two send-now requests for the same post that arrive at the same moment (from Claude and the editor, say) now both answer with the one send they made. Before, the one that lost the race was refused with "post already has an active send", though the send was scheduled and no one was mailed twice; a later repeat already answered this way (SPEC §6).
- A draft deleted elsewhere (in another tab, or by Claude) now says so once and goes to Drafts, instead of failing each save with "Couldn't save your changes". Opening a post that is no longer there goes to Drafts and says so, instead of an error page whose Retry can only fail again. Canceling a scheduled post that was deleted elsewhere says the same, and a Cancel that lands after the send time now says plainly that it's too late and the email is going out, instead of showing the server's refusal (SPEC §4).
- A link in a notification email now opens the send it is about even when you have to sign in first. Before, the sign-in dropped the page from the link and you landed on the dashboard home (SPEC §8).
- Leaving a draft while a save was still going (just after leaving the subject or slug field, say) no longer warns "Changed elsewhere — your edits weren't saved" about your own save, and an edit made while that save was going is no longer lost. The editor now waits for the save to land and saves what is left on top of it.
- A link in a post's Preview tab, or in the sample email on the Template page and in Settings, now opens in a new tab. Before, it loaded in the preview's frame, which went blank when the page refused to be framed, as most do, and the preview was lost until you switched tabs.
- The sample email on the Template page and in Settings no longer runs script a template carries. A template with an inline handler (an image's `onerror`, say) could act in the editor with your session; the sample now shows the template the way the Preview tab shows a post, with nothing in it able to run (SPEC §5).
- On a draft's Preview tab, "Paste, drop, or click to add images" now dims and ignores clicks, like the formatting toolbar. Before, a click there added the image to the hidden Edit text and left the preview unchanged. Dropping an image still works and switches to Edit.
- A send wedged on recipients whose delivery is unknown now keeps its count and its Resolve control until you resolve it. A delivery receipt that named the address but not the message could settle those recipients in its place, so the count you saw shrank, and once the last one was reached the Resolve control vanished and the send sat stuck with nothing in the editor or the API to finish it (SPEC §12).
- The editor's slug field shows only the slug the post actually has. It used to preview a slug from the subject while you typed, and tabbing through the slug field into the body could leave that preview showing a slug another post already held until the next save. The field now updates when the subject is left, with the slug the server gave, numbered if it was taken. Enter in the subject or slug field saves, as leaving it does, and so does ticking the box that has the slug follow the subject. A slug you're typing by hand is never rewritten under the cursor: what it was saved as shows once you leave the field.
- On a checkout with Windows line endings, `npm run sync-migrations` no longer refuses every migration as edited, and `npm run check-context` no longer reports the Claude Code files as having no header.
- `kestrel init` on Windows no longer leaves an extra `claude` folder beside `.claude`, and `npm run check-context -- --merged` accepts a Windows path.
- `npm run check-context` now prints commands that run as written (`npm run check-context -- --update`, `-- --merged`), where it printed a bare `kestrel` that isn't on the path.
- `kestrel init` refuses before writing anything when a migration of the release's is already there, where it wrote the other files first.
- When the web version, a post's Preview tab, or a send's CSV export can't be loaded, the editor now says why, such as "post has no content yet". Before, a deployed instance, served over HTTP/2, showed an empty error box or toast, and a local one only "Not Found" or "Bad Request". A web version address with no post says "There's no post here. It may have been deleted.", and a preview whose post was deleted elsewhere says so. An error page that isn't the API's own, such as a proxy's, now names its HTTP status anywhere in the editor, where it could show a JSON parse error.
- The Worker no longer writes "using deprecated parameters for the initialization function" to its logs the first time it renders an email after starting, a plain-text line among the structured ones.
- The Worker no longer writes "Called .text() on an HTTP body which does not appear to be text" to its logs when a request to the API sends a body that isn't JSON (a form post, say); the request is still refused the same way.

## [1.5.0] - 2026-10-09

**Upgrading from 1.4.0.** No migration. Any script or API client that saves posts must send the revision it read, as `base_revision` or `If-Match`; the editor already does.

### Breaking

- Kestrel now ships as the npm package `@kurtbruns/kestrel`, and the setup guide runs your instance from a small repository of your own that names the release it runs (`npx @kurtbruns/kestrel init`), instead of a copy of Kestrel's repository. An upgrade installs a newer version instead of merging Kestrel's code, and deploying and migrating are plain wrangler commands. A copy of the repository still deploys as before, but the guide no longer covers it (SPEC §11).
- Saving a post through the API now requires the revision the save was based on. A save without one is refused with a 428 `base_required` carrying the post as it stands, instead of overwriting whatever was saved last, so Claude can no longer clobber the publisher's edit by leaving the revision out (SPEC §4).

### Added

- A new instance comes with the `kestrel` command for the instance's scripts: `npm run dev` runs the app locally with the once-a-minute send sweep, `npm run sync-migrations` brings a release's migrations in, `npm run seed` and `npm run reset` load and clear the demo, and `npm run check-context` says when a release changed the Claude Code files the instance started with.
- A new instance starts with Claude Code context for running it (`.claude/CLAUDE.md` and an `/upgrade` skill). It's yours to edit, and an upgrade never overwrites your edits.

## [1.4.0] - 2026-10-08

**Upgrading from 1.3.0.** No migration. If Claude connects through a `.kestrel.env` file, move its three values into `.claude/settings.local.json`, as Connect Claude to the API describes. `.kestrel.env` stays ignored by git. On SES, if bounces and complaints never reach the app, add the SNS topic access policy from the SES guide.

### Changed

- Connecting Claude now keeps the Access service token in `.claude/settings.local.json`, which Claude Code loads into every session and the repository's `.gitignore` now covers. The `.kestrel.env.example` template is gone; an existing `.kestrel.env` stays ignored. The guide also notes that `ACCESS_ALLOWED_EMAILS` doesn't apply to the token, so its Access policy is its only gate.
- The upgrade guide's check after deploying no longer points at all of Verify it works, whose real send would go to your whole list on a live instance; it sends a test email and reads the logs instead. Going back now gives the commands to deploy the previous release before restoring the database.
- The Amazon SES guide now has you let SES publish to the SNS topic, without which no bounce or complaint reaches the app. It also sets the configuration set as your sending hostname's default, and covers the sandbox, production access, and a custom MAIL FROM domain step by step.
- The guides to putting the archive on your website and adding a staging environment are out of the setup guide until they've been run end to end. The configuration reference now says what `ARCHIVE_ORIGIN` and `MEDIA_PUBLIC_BASE` need, including the headers a media custom domain has to send. The More guides section is now Guides.

## [1.3.0] - 2026-10-06

**Upgrading from 1.2.0.** No migration. When you merge the release, keep your own values in the `production` block of `wrangler.jsonc`. To have the deploy attach your hostname, add the template's new `routes`, `workers_dev`, and `preview_urls` lines to that block, with your hostname in `routes`. The template no longer declares a staging environment: if you run one, keep your `staging` block when the merge asks, since your deploys to it still need it. The authoring API has moved under `/api` (see *Breaking*). Your Access application already covers `/api`, so the moved routes stay gated the moment the instance upgrades; afterwards you can remove the four old paths, `posts`, `sends`, `subscribers`, and `suppressions`, from it, leaving `dashboard` and `api`. Any script or Claude setup that calls the old paths must switch to `/api/…`.

### Breaking

- Every authoring API route now lives under `/api`: `/posts…` is `/api/posts…`, and likewise `/sends…`, `/subscribers…`, and `/suppressions…`; the old paths answer `404`. The admin surface is now `/dashboard` and `/api`, so an Access application needs those two paths, and a route added in a later release is gated with nothing to add (SPEC §11).

### Changed

## [1.1.0] - 2026-09-24

**Upgrading from 1.0.0.** This is a minor release that carries breaking changes to the sends API (see *Breaking*): no instance of 1.0.0 was deployed, so the version stays in the 1.x line rather than moving to 2.0.0. It adds one database migration: run `npm run migrate:remote -- --env <name>` before deploying. Update any script or agent prompt that reads sends. For local development, run `npm run migrate:local`; a local database that ran a pre-release build's migrations is rebuilt instead: stop `wrangler dev`, delete `.wrangler/state/v3/d1`, and run `npm run migrate:local`.

### Breaking

- Every sends route now carries a send as one shape, the send's view: `GET /sends` rows, `GET /sends/:id`'s `send`, each feed item, and the answer of schedule, Send now, cancel, reschedule, and Resolve. It holds `status`, the times, `rev`, `as_of`, `audience` (`count`, and whether it is `fixed` at fire), `counts`, `dispatch`, `delivery`, `provider` (with `halt`), `phase`, `conditions`, `actions`, `next_change_at`, and `links`, in place of the flat `c_*` and `halt_*` columns, `recipient_count`, `audience_resolved_at`, the separate `progress` (`state`, `total`), and the raw row. Every action answers `{send, cursor}`, and `GET /sends/:id` answers `{send, outcomes, cursor}`, with the archive link at `send.links.archive` instead of `archive_url`, `published`, and `slug` (SPEC §8).
- `GET /sends/:id/progress` is gone: read `GET /sends/:id`, which answers 304 to `If-None-Match` while the send is unchanged, or follow the feed.
- A send's frozen email is no longer carried on the send (`rendered_html`, `rendered_text`): read it at `GET /sends/:id/email?format=html` or `format=text`.
- Sends report what is wrong with them as `conditions` and what can be done as `actions`, in place of `attention` and `stuck`, on every send's view. Each condition (`missed`, `stuck`, `wedged`, `refused`, `provider_unavailable`, `bounce_spike`, `remade`) carries a severity, when it began, the server's own words, and the action that settles it, if any; `actions` lists exactly the cancel, reschedule, or Resolve the server would take now (SPEC §8).
- A scheduled send can no longer be canceled or rescheduled once its fire time has passed, even before the sweep starts it: the review window closes at the fire time (SPEC §6), and the API answers 409 `window_closed`.
- Scheduling, Send now, cancel, reschedule, and Resolve refuse with a code per reason (`window_closed`, `send_canceled`, `post_not_draft`, `active_send_exists`, `subject_required`, `fire_at_too_soon`, `settings_changed`, `not_wedged`, `run_in_progress`, `count_changed`, `precondition_failed`) instead of `conflict` or `bad_request`, each carrying the send as it stands where there is one.
- Canceling a send that is already canceled answers 200 with `changed: false` instead of a 409, and a reschedule to the time a send already has answers the same way, so a retried request is safe.
- Resolve now works only on a wedged send, and answers 409 `not_wedged` otherwise; before, it could settle ambiguous recipients while others were still waiting to be handed off.
- Every list (`GET /sends`, `/posts`, `/subscribers`, `/sends/:id/deliveries`) refuses a `sort` or `dir` it does not list, or a `limit` or `offset` that is not a whole number, with a 400 naming the field, and `GET /sends` does the same for an unknown `status` or `failures`, instead of quietly reading them as the default.
- `GET /sends/:id/deliveries` now refuses an unknown `view` with a 400 naming the field, instead of quietly showing failures.
- A provider halt's `since` and `retry_at` (under `provider.halt` on a send) are null when the record lacks them, instead of reading as the moment of the request.

### Added

- `GET /sends/feed?since=<cursor>` reports every send that changed since a read of sends, whichever client changed it and whether a write or the clock did (turned due, missed, in flight too long, wedged), each with its phase, counts, and any problem, plus a new cursor and `read_again_at`, when to read again; without `since` it lists the sends that can change on their own. `GET /sends/:id` now carries a `cursor` too, so a client can follow one send from its own read without polling it. A cursor reads `<seq>.<at>` (the change sequence and the server's time at the read), a documented format, so a client holding cursors from several reads can compare them and follow everything from the earliest in one read (SPEC §8).
- `GET /sends` rows carry a `rev` that rises with every change a reader could see of the send, ordered across all sends, and the response carries a `cursor` marking where the read stood (SPEC §8).
- `GET /posts` now carries a `cursor`, where the read stood among the changes to sends, so a client listing posts can follow their sends with `GET /sends/feed` from the same read (SPEC §8).
- `GET /sends/feed` now reports a send deleted with its post under `removed`, so a client drops it instead of keeping a row for a send that is gone (SPEC §8); takes `limit` (default 100, at most 500), and says `more` when a read stopped short, to be read again at once; and gives each send a `next_change_at`, the earliest it can change with no one acting.
- Each `GET /sends/feed` read now lists every open condition across the sends, whether or not they changed, so one read shows every problem.
- `GET /sends/feed` answers a cursor ahead of the database (after a local reset or a restore) with a 409 `cursor_ahead`, and the dashboard and the Sent list then read their sends again, where before such a cursor silently reported nothing ever again.
- Cancel, reschedule, and Resolve take `If-Match: "<rev>"` and refuse with a 412 if the send has changed since the caller read it; Resolve also takes `expected_count`, refused if the number of ambiguous recipients has moved; and cancel and reschedule answers say whether anything `changed`.
- The bounce-spike warning is now worked out by the server and reported on the send, so Claude sees it as the dashboard does, and a re-made scheduled send reports `remade` until a test of its re-made email is sent.
- `MIN_LEAD_SECONDS` sets the minimum lead, how long every send stays cancelable before it fires, per deployment: five minutes when unset, never under one minute in any environment, and never over a day (a value outside that stops the app with an error naming it). Settings shows it read-only, the editor's Schedule, Send now, and Reschedule use it instead of a fixed five minutes, and the API reference states it on the routes that enforce it (SPEC §6). Local dev ships with it at one minute; add `MIN_LEAD_SECONDS="60"` from `.dev.vars.example` to an existing `.dev.vars`.
- `npm run simulate-send -- --in 90s` schedules a demo send on the local dev server through the API (loading the demo first if the database is empty) and prints the link to watch it; it refuses a time inside the minimum lead and says why.
- Local development can model Amazon SES or Resend: `SIMULATE_SENDS` takes `resend`, `ses`, or `1` (the generic simulation), optionally with `:none` for a run with no failures, and Settings names the provider modeled. The SES profile reaches a wedged send and Resolve, and a spent daily quota with its spaced-out retries (SPEC §10). `GET /api/settings` reflects the simulation under `deployment.simulation`.

### Changed

- The setup guide says when it is safe to switch email providers, and the spec states what Kestrel trusts to the people who run it.
- A fire time is now to the minute: schedule, Send now, and reschedule round the requested time up to the next whole minute, when the sweep fires it, and answer with that time, so a countdown ends when the send starts, and the Send now confirmation names that time. The minimum lead is checked on the time as requested, so the review window only grows (SPEC §6).

The dashboard's warnings and the Sent page's attention cards use the server's own words for each problem, and the bounce-spike line links to the send.
- A scheduled send whose fire time has passed now reports the phase `due` until the sweep starts it, instead of `scheduled` (SPEC §12).
- A send is wedged, awaiting Resolve, from the moment the run that left recipients with an unknown fate hands it back, by one rule the send's page, the lists, the feed, the notification, and the log's `send.wedged` all share; before, the log flagged it only after 30 minutes. - The publication logo must now be a PNG, JPEG, WebP, or GIF, the same formats as post images: an SVG upload is refused, since most email apps don't show SVG and the logo rides in every email. A logo already uploaded as an SVG keeps serving until you replace it.

No line carries a subscriber's address or token. The events and their levels are listed in SPEC §12; they replace the old tags (`MISSED_FIRE`, `STUCK_SEND`, `AMBIGUOUS_DELIVERY`, `PROVIDER_REFUSED`, `NOTIFY_FAILED`, `SETTINGS_CORRUPT`, and the rest), so update any saved log search that used them.

The shipped `.dev.vars.example` turns the send simulation on (`SIMULATE_SENDS="resend"`); add it to an existing `.dev.vars`, and `npm run dev` names any setting yours is missing. With the simulation on, test sends and confirmation emails are no longer simulated: they appear in the dev outbox and are never refused.
- Locally, simulated delivery receipts now arrive every couple of seconds on their own, as a provider's webhooks would, instead of at the minute's sweep or while a send's page is open.

Set `SNS_TOPIC_ARN` before adding the SNS subscription (see the setup guide's email sender step).
- The dev-only routes (`/api/dev/token`, `/api/dev/seed`, `/api/dev/reset`, `/api/dev/outbox`) now exist only on a local instance (fake transport, no Access, `APP_ORIGIN` on `localhost` or `127.0.0.1`) and are absent from the API reference everywhere else. Before, a deployed instance left on the fake transport let any signed-in principal wipe its database, and a fake-transport deploy without Access, with `.dev.vars` uploaded as secrets, handed out admin tokens to anyone. Never deploy the top-level (development) config itself: its origin still says `localhost`, so it counts as local dev.
- With no logo uploaded, the built-in template no longer puts a broken image in every email and on its permanent archive page; the sign-off is the name and tagline alone. The Template page and the Settings sample no longer show a stand-in letter tile, so they preview what the email will carry. A custom template can use the new `{{ publication.logo }}`, which renders the logo only when there is one; a template whose `<img>` points at `{{ publication.logoUrl }}` now gets a warning on save, including a saved copy of the old built-in template.
- Through Resend, a second test email of the same post to the same address within a day now goes out: an unchanged post was silently not sent again, and an edited one failed. Each test email is now its own send.
- A send through Resend to 100 or more subscribers now goes out; before, it never left `sending`. Until 1.0.0 the database baseline is edited in place, and this change touches it, so any database that ran the old baseline is rebuilt, not migrated: locally, stop `wrangler dev`, delete `.wrangler/state/v3/d1`, and run `npm run migrate:local`; a deployed database is recreated and `npm run migrate:remote -- --env <name>` run against it (the setup guide's Upgrade step walks through it).
- A large send now spans several sweep ticks, each staying inside Cloudflare's per-invocation limits, instead of being cut off partway through a batch; a Resend batch interrupted after it was accepted is re-sent under the same idempotency key, so no one is mailed twice. The default fits the Workers Free plan; on Workers Paid, set `SUBREQUEST_BUDGET` to 10000 for faster sends (see the setup guide's Provision step).
- A provider outage (Resend or SES down, erroring, or rate-limiting) no longer uses up recipients' retries: the send stays open and retries until the provider is back, and mails everyone exactly once, instead of recording the whole audience unsent after about five minutes and closing as sent (SPEC §12).
- A Resend key that is invalid, revoked, or restricted, a sender that is not verified, a spent Resend sending quota, or an SES account that is paused or suspended now pauses the send with nobody marked unsent, instead of recording the whole audience unsent (one SES request per recipient, each with the same error). The dashboard, the Sent page, and the send's watch show it as one alert carrying the provider's message and what to fix, linked to the send, and the send resumes on its own once the account is fixed; anyone who unsubscribes meanwhile is not mailed. `GET /api/reference` documents the new `halt_*`, `provider.halt`, and `attention.refused` fields. This touches the database baseline, so rebuild the database as described in the Fixed entry about sends through Resend to 100 or more subscribers.
- A confirmation email the provider refuses is no longer treated as sent. The address is left as it was, instead of pending with a link nobody received, so the reader can simply submit the form again; the refusal is logged; and the dashboard's Add subscriber shows the provider's error (SPEC §7).
- A Resend batch whose outcome was unknown (the request failed after it may have been accepted) is no longer re-sent once Resend has forgotten its idempotency key, about a day later; its recipients wait for Resolve instead of risking a second copy.
- Scheduling a post, or sending it now, no longer goes ahead when the save it runs first was refused because the draft had changed elsewhere; it would have frozen the other writer's version. The dialog closes on the out-of-date banner instead, and your unsaved edits are left as they were.
- Uploading or removing the publication logo now updates the confirmation email's preview at once, instead of leaving the old logo there until another field is edited.
- The API reference's method badges (GET/POST/PUT/DELETE) now follow dark mode instead of staying their light-mode colors.
- A malformed API request is now a 400 that names the problem instead of a silent no-op or a server error: a body that is not a JSON object, a field of the wrong type (named in the message and as `field` on the error), and a path with a broken percent-escape. Saving a post with a wrongly typed field, or a `base_revision` that is not a string, is refused instead of saved without that field or without the out-of-date check, and a post save must send a JSON body. A database failure while saving settings is now reported as a server error, not as a bad request.
- A send's delivery record now shows, for each recipient, the worst outcome the provider reported for that send's message (SPEC §8). A test or confirmation email's events no longer land on the recipient's last real delivery, and a `delivered` arriving after a complaint or bounce no longer replaces it. A bounce or complaint reported for `Bob@Example.com` now suppresses the subscriber stored as `bob@example.com`.

## [0.2.0] - 2026-09-21

### Changed

- The migration history is squashed into a single baseline; no deployed database had run the old chain. Until 1.0.0 the baseline is edited in place, so when it changes an existing database is rebuilt, not migrated: delete `.wrangler/state/v3/d1` and run `npm run migrate:local`.
- The send list's status filter no longer accepts `failed`: a send never fails, it keeps retrying and hands the one ambiguous case to you (SPEC §12). The dashboard alert for it, which could never fire, is gone.
- Scheduling a post, or sending it now, keeps you on the post in its scheduled state instead of moving to the Sent page; the confirmation names the fire time.
- The composer's tabs are Edit and Preview, with icons. A scheduled post opens on Preview; its Edit tab keeps the text readable and copyable, says "Cancel the schedule to edit" beneath it (and pulses that line when an edit is attempted), and keeps the formatting toolbar in view, disabled.
- Saving the email template, or a part of the publication identity the template renders (name, tagline, mailing address, logo), while posts are scheduled re-makes their emails, after you confirm, so no scheduled email goes out on an older look; the API asks for an explicit acknowledgement naming the sends, and refuses while a scheduled send is within five minutes of firing. Their content and fire times are untouched, and a re-made send says so until it fires (SPEC §6, §9).
- The Template and Settings pages say, standing, whether the template and identity are in use by scheduled posts, ask before a save that would apply to their emails, and say afterward how many it applied to. A notice on the post and on the dashboard says when a template or identity change was applied to scheduled posts, until you clear it: the first use of the app's dismissible notice.

### Fixed

- A send too large for one sweep tick no longer shows a time to finish that ignores the wait between ticks: the estimate counts the ticks the rest needs, one a minute, so it no longer reads "ETA 26s" with two minutes to go, and the rate reads what a tick carries a minute rather than the burst just after one (SPEC §8).
- An edit typed while the editor was saving in the background read as saved without having been sent, and leaving the page then could lose it. It now stays unsaved and goes with the next save.
- A test or preview of a scheduled post sends its frozen copy, exactly as it will fire, and of a sent post its record, instead of a live render that could differ from either (SPEC §5).
- Two settings writers at once (the identity fields and the logo, or the editor and Claude) no longer overwrite each other's change.
- In the reference room, the tab for the page you are already on (and the Kestrel wordmark on the docs index) now scrolls back to the top instead of doing nothing.

## [0.1.0] - 2026-09-19

The first tagged release: a self-contained newsletter app on a Cloudflare Worker over D1 and R2, with a cron-driven send sweep and a swappable email provider.

### Added

- Markdown authoring with a single render path shared by preview, test, schedule, and send, so a clean test proves exactly what ships.
- Scheduling behind a cancelable review window: the render is frozen and the post soft-locked when scheduled, and stays cancelable until it fires. "Send now" runs the same path after a short cancelable buffer.
- Batched, idempotent delivery: a retry or restart never re-mails a recipient the provider already accepted.
- A double opt-in subscriber list the app owns end to end: consent, one-click unsubscribe, and suppression from bounces and complaints via provider webhooks.
- A permanent per-post public archive (view-in-browser), self-contained on the app's own origin, with an optional archive-on-your-apex enhancement.
- A public reader surface: landing page, archive index, and subscribe / confirm / unsubscribe.
- An admin editor and authoring API behind Cloudflare Access (human SSO plus a service token for Claude), with a local dev token for local-only development.
- Configurable publication identity (name, tagline, logo), email template, and confirmation-email wording, plus default test recipients. Preferences only, never secrets.
- A swappable email-provider seam with a fake in-memory transport for local dev and tests, alongside SES and Resend adapters.
- An in-app reference room: the setup guide and the API reference, served read-only inside the editor.
- A build-version stamp: every instance reports its version, commit, and build time, read-only in the editor and at `GET /api/version`.
- This changelog and a semantic-versioning release process.
