# Changelog

All notable changes to Kestrel are recorded here.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). A version is `MAJOR.RELEASE.PATCH`, which looks like [Semantic Versioning](https://semver.org/spec/v2.0.0.html) but is not: the major changes rarely, at the maintainer's call; the release counts releases and goes up with each one, whether or not it breaks anything; and a patch is fixes only, never a feature or a break. So a release can carry breaking changes without a new major: they are listed under *Breaking*, with what to do in its *Upgrading* paragraph, and moving from `1.1` to `1.2` means reading them. How an entry is written, and how a release is cut, lives in [`.claude/rules/changelog.md`](.claude/rules/changelog.md).

To move a running instance from one version to another, follow [Upgrade to a new release](docs/guides/07-upgrade.md), which is also served in the editor's Docs tab. Read every entry between your version and the target first.

**Upgrading.** One database migration (`0007_sends_progress_at`), which `npm run sync-migrations` brings in: apply it before you deploy with `npx wrangler d1 migrations apply DB --remote --env production` (and `--local` for local development). It adds a column recording when each send last handed anyone off, and writes no rows, so it costs nothing against D1's daily allowance at any size.

### Changed

- A send is flagged as **in flight too long** only when it has handed off no one for 30 minutes and nothing else explains it (a provider refusing the account, an outage it is waiting out, or a send awaiting Resolve), rather than 30 minutes after it started. A large send going out at your SES rate on Workers Free is no longer flagged, emailed about, or logged as `send.stuck`, however long it takes; one the sweep has stopped moving still is, shows no time to finish, and its email and message say nothing has gone out and why that points at the sweep (SPEC §12).

### Fixed

- A send that SES keeps partly refusing, as a daily quota frees up a few at a time, is one refusal until SES takes a batch with nothing refused: you're emailed about it once, its page keeps the time the refusal began, and its retries keep spacing out up to an hour apart instead of starting over every few minutes. The readers SES took are still recorded as sent at once, and the rest wait with no retry spent (SPEC §12).
- A send paused for a provider outage reads **Backing off**, with when it next retries, on its page, the Sent list, and the dashboard, and shows no time to finish, even while a batch the provider never answered waits for Resolve. Before, it read as sending normally for up to an hour (SPEC §12).

## [1.10.0] - 2026-10-14

**Upgrading from 1.9.0.** No database migrations. Run `npm run check-context` in your instance's repository: this release changes the operator's Claude context (a new `/migrate-list` skill, and rules for erasing, for choosing between unsubscribing and blocking, and for reading the docs as Markdown), and a copy you've edited is merged by hand. Three API changes can break a script of yours, listed under Breaking. One that adds suppressions sends `reason: "manual"` or none, reads what was stored from the answer's `suppression`, and takes a 200 with `added: false` as already suppressed. One that clears suppressions takes a 409 `erasure_marker` on an erased address as final. One that reads `GET /api/docs` reads `sets` in place of `landing`.

### Added

- The docs are now two sets, each with its own index: **Publishing**, for whoever writes and sends the newsletter, and **Self-hosting**, the setup guide. The editor's Docs tab opens on Publishing, under a **Kestrel docs** header, one intro for both sets, and a tab per set, and each page names its set over its title. Publishing opens with **Set up your publication**, which follows the dashboard's first-run checklist of the same name step for step (Name your publication, Check your setup, Bring your existing list, Write your first post, Share your subscribe link), then **Sending** (Scheduling and sending, After a send, Sending rules) and **More** (Working with Claude, the import format). Sending rules says what the law asks of a newsletter, who handles each part, and how to act on a reader's request to leave or be deleted. Name your publication says when to provide a mailing address, and the address's hints and warning in Settings, and the template's save warning, now link that section in a new tab. The import format reference moves from Self-hosting into Publishing, keeping its address in the Docs tab (SPEC §9, §11).
- The docs and the API reference are served as Markdown for an agent to read: `GET /api/docs/<slug>.md` for a page, `GET /api/docs/publishing.md` and `GET /api/docs/self-hosting.md` for each set's index, and `GET /api/reference.md` for the whole reference, generated from the same registration as the JSON. Links between docs point at each other's Markdown. Connect Claude to the API mentions them (SPEC §11).
- The operator's Claude context reads the docs as Markdown: its CLAUDE.md names the two sets and the Markdown routes, and `/migrate-list` reads the import format and "Bring your existing list" at `GET /api/docs/import-format.md` and `GET /api/docs/your-list.md`, since the import format reference moved into the publisher's pages. `npm run check-context` offers the change to an existing instance.
- **Block** and **Unblock** in a subscriber's ⋯ menu on the Subscribers page, for your own decision to stop mailing an address, as opposed to theirs. Unsubscribe is for when they ask to leave, and its dialog now says so; a block keeps their status and can be undone. The Legend lists each act and when it's the one to use (SPEC §7).
- The operator's Claude context gains a rule for choosing between unsubscribing and blocking: unsubscribe only when the person asked, block when you decide yourself, unblock or clear only an address you name, and never clear a bounce or complaint without your word. It bears on safety, since clearing one lets mail go to an address that failed or reported spam.
- Bring your list in and take it out from the dashboard. **Subscribers → Import** shows the file Kestrel reads (a full CSV or a plain list, each with an example file), plans a file the moment you choose it, and shows what will happen to every row, with any rows your list keeps as they are set apart, the rows not imported as subscribers to download, and the Workers Free daily-writes warning when it applies. You attest, acknowledge each scheduled post that would grow, and import, and the result says nobody was emailed. **Export** downloads the whole list as one CSV in the same format. The subscriber list gains a **How they joined** column ("Imported · Sendy, single opt-in", or "Double opt-in" for a confirmation Kestrel recorded) and **View subscriber** in each row's menu shows how they joined, with the evidence. "Bring your existing list", in the Docs tab's new **Publishing** docs, explains it all, and Claude reads the same page (SPEC §7, §8).
- The operator's Claude context gains a `/migrate-list` skill, which `kestrel init` writes and `npm run check-context` offers to an existing instance, so Claude can bring a list over from another service by a method that checks itself against Kestrel's import plan, and explains the format, the row limit, and the Workers Free advice from the publisher page "Bring your existing list" in the in-app docs rather than in its own words. It bears on safety, since it adds subscribers: the rule against adding a subscriber the publisher didn't name now makes one exception, for such an import, confirming anyone only with the publisher's attestation.
- Erase a subscriber, for a reader who asks you to delete their data: Erase in the Subscribers row menu, or `POST /api/subscribers/:id/erase`. It removes their subscriber record, with how they joined and its evidence, shows an erased recipient in their place on every past send so each record still adds up, and keeps the address only as a do-not-contact suppression, which no import lifts or gets past: while the address carries it, or when the file itself marks the address as erased, an import creates no subscriber for it, whatever status the file gives it, and a file that marks a pending subscriber as erased leaves them pending, never confirmed. It can't be undone. The person can still rejoin by subscribing and confirming themselves; adding the address by hand asks you first (`acknowledge_erasure: true` through the API) (SPEC §7).
- The operator's Claude context gains a rule for erasing: Claude erases a subscriber only when you name them and ask, confirming first since it can't be undone, and sends a confirmation to an erased address only once you say the person asked to join again. It bears on safety, since an erasure is permanent.

### Changed

- The dashboard's first-run checklist speaks to the publisher: its second step, once an email provider is connected, is **Check your setup**, which opens a new Publishing page on sending yourself a test, how Kestrel tells you when something needs attention, and what changes as your list grows, in place of confirming the sending domain. It also gains **Bring your existing list**, before writing the first post, with **Import** for a publisher moving from another service; a fresh publication skips it. The checklist now stays until the first post rather than ending at the first subscriber, so importing a list no longer takes away the steps after it, and the list step shows as done with the count of subscribers on your list.
- On the Subscribers page, each count in the summary filters the list: choose **confirmed**, **pending**, or **unsubscribed** to see that status, or **suppressed** to see every suppressed subscriber, and choose it again to see everyone. The suppressed count, here and on the dashboard, now counts suppressed subscribers rather than every suppressed address, so it matches the rows its filter shows (SPEC §8).
- On the Subscribers page, the status and suppression pills no longer explain themselves in a hover tooltip, which keyboard, screen-reader, and touch users couldn't reach. A **Legend** beside the counts opens to show each pill beside what it means: the consent states, what suppressed means, and each red flag (bounced, complaint, blocked, erased). It replaces the counts' info tip, and the provider's words for a bounce or complaint, which the flag's tooltip carried, now show in **View subscriber**. The API reference describes subscriber states, suppression reasons, and each act on a subscriber in the same words, so Claude is told what you are told.
- The other labels that explained themselves only on hover now say it on the page. On a sent post's record, the line accounting for every recipient says that a hard bounce or a complaint suppresses the address and a soft bounce leaves it on the list, where a row's outcome used to say it in a tooltip. On the Template page and the Settings template section, while a post is about to send, the lede says when it sends and that you can save once it has, which the in-use chip's tooltip used to, and the sentence goes away once that time has passed. Pills and chips across the editor show the ordinary arrow cursor rather than a text cursor.
- The Subscribers table holds up at mid-sized widths: it switches to stacked rows whenever it's too narrow to give an address room, not only at phone width, the How they joined column is narrower, and an address that has to wrap breaks before its @ rather than mid-word.
- The import attestation names your publication the way the sidebar and your emails do: until you set a publication name, by the display name of your From address, and only with neither as "this newsletter". The plan's `attestation` carries the `publication` name it used, and the dashboard's import screen takes the name under the attestation from there. The attestation's version is unchanged.
- The import format's example files download as `kestrel-import-example.csv` and `kestrel-import-example.txt`, so one isn't mistaken for an exported list, and on the Workers Free plan's limits the row-limit reason (`limits.max_rows_reason`, also in a `too_many_rows` refusal) now speaks to the publisher: it's Cloudflare's free plan's limit, and whoever runs their Kestrel can raise it to 10,000 rows by moving to Workers Paid. The import format reference says how a CSV quotes a value in plain words (SPEC §7).
- On the Subscribers page, a suppressed subscriber's status shows in the unsubscribed grey, so a confirmed address that bounced, complained, or was blocked no longer shows a green "confirmed" while it isn't mailed; the red flag beside the address still says why. The status itself is unchanged, and clearing the suppression puts it back in effect.
- The demo loaded by `npm run seed` (without `--size`) now has a suppression on every consent state: besides the bounced and complained confirmed readers, an unsubscribed reader and a pending sign-up blocked by hand, and an erased person who subscribed again. The list's audience and past sends are as before.
- Dates in the editor show their year when it isn't the current year, past or future, so a draft last edited in a previous year, a send from last year, or a send scheduled for next January reads unambiguously ("Jun 15, 2025, 8:06 AM"); this year's dates stay as short as before.
- Readers can reply. The setup guide's Connect Amazon SES gains a step, "Receive replies at your From address", that forwards the From address to your inbox with Cloudflare Email Routing, where before nothing received mail there and a reply most likely bounced; Verify it works now has you reply to your test email. Kestrel still only sends: it never receives or stores a reply. An existing instance can add the forwarding at any time, with no redeploy. The new step is section 3, so Connect Amazon SES's later sections move down one (Request production access is now 5, Subscribe the app to the topic now 9), and a link to one of them by its old anchor (such as `#4-request-production-access`) now opens the top of the page instead. Settings says under the From address that readers' replies go there, linking the step (SPEC §9).
- On the Workers Free plan's limits, the daily-writes warnings now count what the day's imports wrote, by UTC. An import plan warns when it and that day's earlier imports would use more than 70% of D1's daily writes, and advises importing the file the next day, so a list brought in over several files is warned before it can stop the newsletter. A scheduled send firing on a day imports have written now warns below 5,000 recipients, and advises sending the next day. The plan no longer warns because the list it leaves passes 3,000 confirmed subscribers: whether a send fits is the send's warning, given when it's scheduled (SPEC §7, §8).

### Fixed

- On the Subscribers page, an address whose bounce or complaint came in with an import is flagged **bounced** or **complaint**, like one seen here, rather than a bare **suppressed**.
- On a list with more than 1,000 suppressions, the Subscribers page now flags every suppressed address: one suppressed before the newest 1,000 showed as not suppressed, with no red flag, a live-coloured status, and Block offered in its row menu. `GET /api/subscribers` now reads each row's suppression for the page's own addresses.

### Breaking

- `GET /api/docs` returns `sets` (each set's id, name, title, intro, and sections) in place of the single `landing`, and each doc carries the `set` it belongs to. A section's id is now its heading's anchor rather than its folder (SPEC §11).
- `counts.suppressed` in `GET /api/subscribers` counts subscribers whose address is suppressed, whatever their status, rather than every suppressed address, so it matches `suppressed=only`; an address suppressed with no subscriber is counted only in `GET /api/suppressions` (SPEC §8).
- `POST /api/suppressions` adds only a block: `reason` may be omitted or `manual`, and any other is refused 400, since a bounce or complaint is the provider's to report and an erasure's marker is Erase's to leave. An address already suppressed keeps what it has, and the answer is now the suppression that stands with `added`, instead of echoing the request. `DELETE /api/suppressions/:email` refuses an erased address's marker with 409 `erasure_marker`, which only the person's own confirmation lifts (SPEC §7).

## [1.9.0] - 2026-10-13

**Upgrading from 1.8.0.** Two database migrations: run `npm run sync-migrations`, then `npx wrangler d1 migrations apply DB --remote --env production` (and `--local` for local development) before deploying. The first (`0005_imports`) adds the record of each import and how each subscriber joined, reading every existing subscriber as joined through Kestrel's double opt-in, and rebuilds the notifications table so an import can be told to you. The second (`0006_deliveries_fewer_indexes`) drops two indexes no query reads; it writes no rows, so it costs nothing against D1's daily allowance at any size.

### Added

- Bring an existing list in, and take the whole list out, through the API, in one documented format, `kestrel-subscribers/1` (a CSV, or a plain `.txt` list of addresses). A plan shows what the import would do to every address before anything changes; the commit applies it whole, with your attestation that everyone imported as subscribed opted in, and imports them as confirmed with how and where they joined, never reversing an unsubscribe (even for a reader the subscribe form has put back to pending) or lifting a suppression here, and sending no email. Each subscriber now records how they joined beside their state; Claude may attest for you, and you're emailed when it does, but only a person can let an import grow a scheduled send. The export reads the list out in the same format, a page at a time (1,000 rows on the Workers Free plan's limits, 10,000 otherwise), with every address on the list for the whole export appearing exactly once, so another instance imports it back; in the CSV written from its pages, a value a spreadsheet would run as a formula is written as text. One import takes up to 10,000 rows, or 1,000 on the Workers Free plan's limits (`SUBREQUEST_BUDGET` unset). The format's reference is in the Docs tab and at `GET /api/imports/format` (SPEC §7, §8).
- On the Workers Free plan's limits (`SUBREQUEST_BUDGET` unset), where D1 refuses every query once a day's 100,000 written rows are spent and the instance stops until midnight UTC, the app now warns before it gets there. A send to more than 5,000 recipients says so in the Schedule dialog, on the scheduled post, and to Claude as the send's `daily_writes` condition. An import plan that would leave more than 3,000 confirmed subscribers advises sending the next day (UTC). Neither warning ever refuses. The setup guide now recommends Workers Paid from about 5,000 subscribers, for the database's writes as well as send speed (SPEC §7, §8).

### Changed

- While no email provider is connected, a scheduled post's banner says "Will be held" in the banner's own violet, led by an amber ⚠️, the same look as its daily-writes line, instead of amber text on violet, which fell short of readable contrast. The dashboard's scheduled card keeps its amber line.
- A send uses fewer of D1's rows: about 14 written and 41 read per recipient, receipts included, down from about 16 and 118. On the Workers Free plan, whose D1 refuses every query once a day's 100,000 written rows are spent, one send can now reach about 7,000 subscribers in a day instead of about 6,200. On Workers Paid, a send bills fewer writes and leaves a smaller database.
- The API's refusals and render warnings that the editor shows read as sentences that name the next step, with typographic apostrophes and no em dashes: a save or image upload on a scheduled post, a test with no recipients or too many, an address Settings won't take, a scheduling or Resolve refusal, a warning such as an image with no alt text. A template test's refusals about its recipients now name `to` as their `field`, and a save, delete, or image change on a post that isn't a draft is refused as 409 `post_not_draft` instead of `conflict`, saying whether canceling the schedule would unlock it or its send has already started.
- A send time inside the minimum lead is refused in one plain sentence, "Pick a time at least 5 minutes from now, so there’s time to cancel.", which is now the API's own message on scheduling and rescheduling alike, so Claude reads what the publisher reads where it used to read the route to call; Send now remains the soonest send (SPEC §6).
- The Schedule dialog's Send now row reads "Or send as soon as possible.", and the Send now view says when the send goes out (one lead, up to the next minute), that the post locks until then, and that it can be canceled before it starts sending, counting recipients as the scheduled card does rather than "confirmed subscribers". The Schedule and Reschedule hints no longer name the lead, which the refusal states when a time is too soon, and the post's scheduled banner drops "cancelable until then", which its Cancel button and countdown already say.

### Fixed

- A list send whose `SES_CONFIGURATION_SET` names a configuration set SES can't find in its region is held with nobody consumed, as a new `configuration` cause whose advice names the setting, where before SES's `NotFoundException` marked every recipient unsent, and its per-recipient form advised replacing the access key (SPEC §12).

## [1.8.0] - 2026-10-12

**Upgrading from 1.7.0.** Do these in order. First, if your `production` block sets `PROVIDER` to `resend`, switch it to SES on the release you run now, while no send is sending, as [Connect Amazon SES](docs/get-started/04-ses.md#switch-an-instance-that-already-sends) describes, and upgrade only after that: this release refuses `resend`, and until the switch the public pages say the newsletter is temporarily unavailable and nothing is sent. From the switch on, the app no longer records the bounces and complaints Resend reports, so if you can, let a few days pass after your last Resend send before you switch. Then delete the `RESEND_API_KEY` and `RESEND_WEBHOOK_SECRET` secrets and the Resend webhook. Second, if you send through SES, make the `Action` of your sending key's IAM policy (Connect Amazon SES's `kestrel-send-email`) `["ses:SendEmail", "ses:SendBulkEmail"]` before you deploy, where 1.7.0's guide gave only `ses:SendEmail`: this release sends through SES's bulk API, and until the key may call it every list send is held as SES refusing the credentials, while a test email still goes out, so a test won't show it's missing. You may also add **Rendering failures** to your configuration set's event destination, so the app can log one. Third, before you commit the upgrade, as they apply to you: if your `production` block sets `PROVIDER` to `fake` on a real hostname, this release refuses it: set your email provider, or make it `""` until you [connect one](docs/get-started/04-ses.md). A hosted demo that runs `fake` on a real hostname on purpose adds `ALLOW_FAKE_PROVIDER: "true"` before it upgrades, to the env it hands Kestrel: its `vars`, or the object it builds if it builds one, and that object's type. If your `production` block has no `PROVIDER` line, you may add `"PROVIDER": ""` to its `vars` to quiet wrangler's warning that it's missing there; it means the same as leaving it out. If sign-in to a deployed instance has been failing, store `ACCESS_TEAM_DOMAIN` again as the bare hostname (like `yourteam.cloudflareaccess.com`): a value this release still can't read as a hostname, such as one with a path or a port, is now refused, and until it's fixed the public pages say the newsletter is temporarily unavailable and nothing is sent, where before only sign-in failed. A local `.dev.vars` with `SIMULATE_SENDS` set to `resend` (or `resend:none`) changes it to `ses` (or `ses:none`). Fourth, one database migration, which `npm run sync-migrations` brings in before you commit the upgrade: apply it after noting a restore point and before you deploy, as [Upgrade to a new release](docs/guides/07-upgrade.md) does, with `npx wrangler d1 migrations apply DB --remote --env production` (and `--local` for local development). It moves any recipients a send left queued to be re-sent under an earlier provider's key into flight, where **Resolve** settles them, rather than leaving the send open and silent; on a database with none it changes nothing.

### Breaking

- Resend is no longer supported, so Amazon SES is the one email provider. `PROVIDER=resend` is refused, naming the step that switches to SES; `/webhooks/resend` is gone; and `SIMULATE_SENDS=resend` is refused in local development. Resend sells newsletters as Broadcasts, which would hand it the list and the record of who was mailed (SPEC §10). With no provider left that dedupes a repeated request, a batch whose answer never came always waits for Resolve; before, on Resend, it was sent again under its key (SPEC §12).
- Sending through SES needs `ses:SendBulkEmail` in the sending key's IAM policy, where `ses:SendEmail` was enough before. On a key without it, SES refuses every list send, and each send is held with nobody consumed, as a credentials refusal, until the policy allows it; the refusal's advice says to give the key both permissions or replace it (SPEC §12). Tests and confirmations still go out, so a test email won't reveal a missing permission.
- `PROVIDER` set to `fake` is now refused unless `APP_ORIGIN` is on `localhost` or `127.0.0.1`, naming `PROVIDER`, so the development value copied into production, which wrangler's warning about a var missing from `production` invites, shows at Deploy's check instead of opening signups whose confirmations go nowhere and recording sends no one receives. A hosted demo that runs `fake` on purpose opts in with `ALLOW_FAKE_PROVIDER` set to `true`, which no other provider reads (SPEC §9).

### Added

- Local development can run as a deployment with no email provider connected: `SIMULATE_SENDS=not-connected` refuses every send, closes signups, and holds a due send, which goes out at its next retry once the switch is off, with local sign-in still on, so the editor's not-connected state can be seen without deploying. A deployed instance ignores it (SPEC §10).
- While no email provider is connected, the editor says so where sending would otherwise look possible: a draft's page notes it can be written and previewed but not sent, and a scheduled send's dashboard card and editor banner say it will be held when it fires. `kestrel dev` prints a line naming what `SIMULATE_SENDS` makes of the run, `not-connected` or a simulated provider, since wrangler shows the variable only as "(hidden)".

### Changed

- The setup guide walks through Amazon SES. Get started's step 3 is now Connect Amazon SES, which replaces Connect an email provider (Resend) and takes over the Use Amazon SES instead of Resend guide. The editor's links to the setup step, the dashboard's setup checklist, and the notification email name it and open it, and local development simulates SES by default. Connect Amazon SES says where to read your region's code and your account ID, walks through creating the sending policy in its own browser tab, shows the `production` vars as they end up, and gives the IAM user, configuration set, and SNS topic distinct names. It says to name the publication before requesting production access, since AWS may visit the site, and what to tell AWS if it asks for more detail. For an SNS subscription stuck pending, it puts Access covering the webhook first among the reasons, and has you choose **Request confirmation**, since SNS won't let you delete it. Go live first checks that SES production access came through and the send rate is raised from the sandbox's `1`, and says how fast a send goes out and when to raise the send rate or the Workers plan. The Sending-domain DNS reference speaks of SES's three checks, where SPF needs a record only with a custom MAIL FROM domain.
- SES now takes a batch a request through its bulk API: one second of your account's send rate, up to 50 recipients, one request a second. On Workers Free a minute sends 56 recipients at a send rate of 14 and 200 at 50 or more, where it sent about 18, so SES no longer needs Workers Paid, and the setup guide says to raise the account's send rate to 50 before changing plans. Each reader's email, unsubscribe link, and one-click headers are as before, and a test, a confirmation, or a notification goes through SES's single-send API with the same template, so it is the same email without queuing behind the bulk API's one request a second. A request SES never answers now holds the send for an outage's backoff, so an unreachable SES leaves one batch for Resolve rather than one every minute. Recipients SES holds back for a throttle or a spent quota go back to the queue without spending one of their attempts, and the send says why. A request lost in flight now leaves its whole batch for Resolve rather than one recipient, and an email SES took but couldn't build is logged as `webhook.render_failed` (SPEC §10, §12).
- A new instance's `production` settings declare `"PROVIDER": ""`, which means no provider connected, so wrangler no longer warns on every production command that `PROVIDER` is missing there. Connect Amazon SES now says to change it rather than add it.
- Resolve, the wedged-send notification, and Connect Amazon SES say that Kestrel can't tell whether a lost request's emails went out, so unless you know, Assume not sent is the safe default, and Assume sent is for when you know otherwise, such as a reader who says they got it. Before, they said to check the provider's console, which shows sent messages only with SES's Virtual Deliverability Manager turned on. The Resolve dialog also says Assume sent records the recipients as accepted by your provider, with delivery still waiting on a receipt, rather than as delivered (SPEC §12).
- The operator's Claude context (`.claude/CLAUDE.md` in a new instance) carries a new safety caution: `PROVIDER` stays `""` in production until Connect Amazon SES sets it to `ses`, and is never `fake`, whatever a wrangler warning suggests, so an instance's Claude doesn't "fix" the warning by copying the development value into production. `npm run check-context` reports the change; if you edited your `.claude/CLAUDE.md`, merge the line by hand.

## [1.1.0] - 2026-09-24

**Upgrading from 1.0.0.** This is a minor release that carries breaking changes to the sends API (see *Breaking*): no instance of 1.0.0 was deployed, so the version stays in the 1.x line rather than moving to 2.0.0. It adds one database migration: run `npm run migrate:remote -- --env <name>` before deploying. Update any script or agent prompt that reads sends. For local development, run `npm run migrate:local`; a local database that ran a pre-release build's migrations is rebuilt instead: stop `wrangler dev`, delete `.wrangler/state/v3/d1`, and run `npm run migrate:local`.

### Breaking

- Every sends route now carries a send as one shape, the send's view: `GET /sends` rows, `GET /sends/:id`'s `send`, each feed item, and the answer of schedule, Send now, cancel, reschedule, and Resolve. It holds `status`, the times, `rev`, `as_of`, `audience` (`count`, and whether it is `fixed` at fire), `counts`, `dispatch`, `delivery`, `provider` (with `halt`), `phase`, `conditions`, `actions`, `next_change_at`, and `links`, in place of the flat `c_*` and `halt_*` columns, `recipient_count`, `audience_resolved_at`, the separate `progress` (`state`, `total`), and the raw row. Every action answers `{send, cursor}`, and `GET /sends/:id` answers `{send, outcomes, cursor}`, with the archive link at `send.links.archive` instead of `archive_url`, `published`, and `slug` (SPEC §8).
- `GET /sends/:id/progress` is gone: read `GET /sends/:id`, which answers 304 to `If-None-Match` while the send is unchanged, or follow the feed.
- A send's frozen email is no longer carried on the send (`rendered_html`, `rendered_text`): read it at `GET /sends/:id/email?format=html` or `format=text`.
- Sends report what is wrong with them as `conditions` and what can be done as `actions`, in place of `attention` and `stuck`, on every send's view. Each condition (`missed`, `stuck`, `wedged`, `refused`, `provider_unavailable`, `bounce_spike`, `remade`) carries a severity, when it began, the server's own words, and the action that settles it, if any; `actions` lists exactly the cancel, reschedule, or Resolve the server would take now (SPEC §8).
- A scheduled send can no longer be canceled or rescheduled once its fire time has passed, even before the sweep starts it: the review window closes at the fire time (SPEC §6), and the API answers 409 `window_closed`.
- Scheduling, Send now, cancel, reschedule, and Resolve refuse with a code per reason (`window_closed`, `send_canceled`, `post_not_draft`, `active_send_exists`, `subject_required`, `fire_at_too_soon`, `settings_changed`, `not_wedged`, `run_in_progress`, `count_changed`, `precondition_failed`) instead of `conflict` or `bad_request`, each carrying the send as it stands where there is one.
- Canceling a send that is already canceled answers 200 with `changed: false` instead of a 409, and a reschedule to the time a send already has answers the same way, so a retried request is safe.
- Resolve now works only on a wedged send, and answers 409 `not_wedged` otherwise; before, it could settle ambiguous recipients while others were still waiting to be handed off.
- Every list (`GET /sends`, `/posts`, `/subscribers`, `/sends/:id/deliveries`) refuses a `sort` or `dir` it does not list, or a `limit` or `offset` that is not a whole number, with a 400 naming the field, and `GET /sends` does the same for an unknown `status` or `failures`, instead of quietly reading them as the default.
- `GET /sends/:id/deliveries` now refuses an unknown `view` with a 400 naming the field, instead of quietly showing failures.
- A provider halt's `since` and `retry_at` (under `provider.halt` on a send) are null when the record lacks them, instead of reading as the moment of the request.

### Added

- `GET /sends/feed?since=<cursor>` reports every send that changed since a read of sends, whichever client changed it and whether a write or the clock did (turned due, missed, in flight too long, wedged), each with its phase, counts, and any problem, plus a new cursor and `read_again_at`, when to read again; without `since` it lists the sends that can change on their own. `GET /sends/:id` now carries a `cursor` too, so a client can follow one send from its own read without polling it. A cursor reads `<seq>.<at>` (the change sequence and the server's time at the read), a documented format, so a client holding cursors from several reads can compare them and follow everything from the earliest in one read (SPEC §8).
- `GET /sends` rows carry a `rev` that rises with every change a reader could see of the send, ordered across all sends, and the response carries a `cursor` marking where the read stood (SPEC §8).
- `GET /posts` now carries a `cursor`, where the read stood among the changes to sends, so a client listing posts can follow their sends with `GET /sends/feed` from the same read (SPEC §8).
- `GET /sends/feed` now reports a send deleted with its post under `removed`, so a client drops it instead of keeping a row for a send that is gone (SPEC §8); takes `limit` (default 100, at most 500), and says `more` when a read stopped short, to be read again at once; and gives each send a `next_change_at`, the earliest it can change with no one acting.
- Each `GET /sends/feed` read now lists every open condition across the sends, whether or not they changed, so one read shows every problem.
- `GET /sends/feed` answers a cursor ahead of the database (after a local reset or a restore) with a 409 `cursor_ahead`, and the dashboard and the Sent list then read their sends again, where before such a cursor silently reported nothing ever again.
- Cancel, reschedule, and Resolve take `If-Match: "<rev>"` and refuse with a 412 if the send has changed since the caller read it; Resolve also takes `expected_count`, refused if the number of ambiguous recipients has moved; and cancel and reschedule answers say whether anything `changed`.
- The bounce-spike warning is now worked out by the server and reported on the send, so Claude sees it as the dashboard does, and a re-made scheduled send reports `remade` until a test of its re-made email is sent.
- `MIN_LEAD_SECONDS` sets the minimum lead, how long every send stays cancelable before it fires, per deployment: five minutes when unset, never under one minute in any environment, and never over a day (a value outside that stops the app with an error naming it). Settings shows it read-only, the editor's Schedule, Send now, and Reschedule use it instead of a fixed five minutes, and the API reference states it on the routes that enforce it (SPEC §6). Local dev ships with it at one minute; add `MIN_LEAD_SECONDS="60"` from `.dev.vars.example` to an existing `.dev.vars`.
- `npm run simulate-send -- --in 90s` schedules a demo send on the local dev server through the API (loading the demo first if the database is empty) and prints the link to watch it; it refuses a time inside the minimum lead and says why.
- Local development can model Amazon SES or Resend: `SIMULATE_SENDS` takes `resend`, `ses`, or `1` (the generic simulation), optionally with `:none` for a run with no failures, and Settings names the provider modeled. The SES profile reaches a wedged send and Resolve, and a spent daily quota with its spaced-out retries (SPEC §10). `GET /api/settings` reflects the simulation under `deployment.simulation`.

Before, any correctly signed SNS message was trusted, so a topic in someone else's AWS account could subscribe the endpoint and suppress addresses on your list with forged bounces. Set `SNS_TOPIC_ARN` before adding the SNS subscription (see the setup guide's email sender step).
- The dev-only routes (`/api/dev/token`, `/api/dev/seed`, `/api/dev/reset`, `/api/dev/outbox`) now exist only on a local instance (fake transport, no Access, `APP_ORIGIN` on `localhost` or `127.0.0.1`) and are absent from the API reference everywhere else. Before, a deployed instance left on the fake transport let any signed-in principal wipe its database, and a fake-transport deploy without Access, with `.dev.vars` uploaded as secrets, handed out admin tokens to anyone. Never deploy the top-level (development) config itself: its origin still says `localhost`, so it counts as local dev.
- With no logo uploaded, the built-in template no longer puts a broken image in every email and on its permanent archive page; the sign-off is the name and tagline alone. The Template page and the Settings sample no longer show a stand-in letter tile, so they preview what the email will carry. A custom template can use the new `{{ publication.logo }}`, which renders the logo only when there is one; a template whose `<img>` points at `{{ publication.logoUrl }}` now gets a warning on save, including a saved copy of the old built-in template.
- Through Resend, a second test email of the same post to the same address within a day now goes out: an unchanged post was silently not sent again, and an edited one failed. Each test email is now its own send.
- A send through Resend to 100 or more subscribers now goes out; before, it never left `sending`. Until 1.0.0 the database baseline is edited in place, and this change touches it, so any database that ran the old baseline is rebuilt, not migrated: locally, stop `wrangler dev`, delete `.wrangler/state/v3/d1`, and run `npm run migrate:local`; a deployed database is recreated and `npm run migrate:remote -- --env <name>` run against it (the setup guide's Upgrade step walks through it).
- A large send now spans several sweep ticks, each staying inside Cloudflare's per-invocation limits, instead of being cut off partway through a batch; a Resend batch interrupted after it was accepted is re-sent under the same idempotency key, so no one is mailed twice. The default fits the Workers Free plan; on Workers Paid, set `SUBREQUEST_BUDGET` to 10000 for faster sends (see the setup guide's Provision step).
- A provider outage (Resend or SES down, erroring, or rate-limiting) no longer uses up recipients' retries: the send stays open and retries until the provider is back, and mails everyone exactly once, instead of recording the whole audience unsent after about five minutes and closing as sent (SPEC §12).
- A Resend key that is invalid, revoked, or restricted, a sender that is not verified, a spent Resend sending quota, or an SES account that is paused or suspended now pauses the send with nobody marked unsent, instead of recording the whole audience unsent (one SES request per recipient, each with the same error). The dashboard, the Sent page, and the send's watch show it as one alert carrying the provider's message and what to fix, linked to the send, and the send resumes on its own once the account is fixed; anyone who unsubscribes meanwhile is not mailed. `GET /api/reference` documents the new `halt_*`, `provider.halt`, and `attention.refused` fields. This touches the database baseline, so rebuild the database as described in the Fixed entry about sends through Resend to 100 or more subscribers.
- A confirmation email the provider refuses is no longer treated as sent. The address is left as it was, instead of pending with a link nobody received, so the reader can simply submit the form again; the refusal is logged; and the dashboard's Add subscriber shows the provider's error (SPEC §7).
- A Resend batch whose outcome was unknown (the request failed after it may have been accepted) is no longer re-sent once Resend has forgotten its idempotency key, about a day later; its recipients wait for Resolve instead of risking a second copy.
- Scheduling a post, or sending it now, no longer goes ahead when the save it runs first was refused because the draft had changed elsewhere; it would have frozen the other writer's version. The dialog closes on the out-of-date banner instead, and your unsaved edits are left as they were.
- Uploading or removing the publication logo now updates the confirmation email's preview at once, instead of leaving the old logo there until another field is edited.
- The API reference's method badges (GET/POST/PUT/DELETE) now follow dark mode instead of staying their light-mode colors.
- A malformed API request is now a 400 that names the problem instead of a silent no-op or a server error: a body that is not a JSON object, a field of the wrong type (named in the message and as `field` on the error), and a path with a broken percent-escape. Saving a post with a wrongly typed field, or a `base_revision` that is not a string, is refused instead of saved without that field or without the out-of-date check, and a post save must send a JSON body. A database failure while saving settings is now reported as a server error, not as a bad request.
- A send's delivery record now shows, for each recipient, the worst outcome the provider reported for that send's message (SPEC §8). A test or confirmation email's events no longer land on the recipient's last real delivery, and a `delivered` arriving after a complaint or bounce no longer replaces it. A bounce or complaint reported for `Bob@Example.com` now suppresses the subscriber stored as `bob@example.com`.

## [0.2.0] - 2026-09-21

### Changed

- The migration history is squashed into a single baseline; no deployed database had run the old chain. Until 1.0.0 the baseline is edited in place, so when it changes an existing database is rebuilt, not migrated: delete `.wrangler/state/v3/d1` and run `npm run migrate:local`.
- The send list's status filter no longer accepts `failed`: a send never fails, it keeps retrying and hands the one ambiguous case to you (SPEC §12). The dashboard alert for it, which could never fire, is gone.
- Scheduling a post, or sending it now, keeps you on the post in its scheduled state instead of moving to the Sent page; the confirmation names the fire time.
- The composer's tabs are Edit and Preview, with icons. A scheduled post opens on Preview; its Edit tab keeps the text readable and copyable, says "Cancel the schedule to edit" beneath it (and pulses that line when an edit is attempted), and keeps the formatting toolbar in view, disabled.
- Saving the email template, or a part of the publication identity the template renders (name, tagline, mailing address, logo), while posts are scheduled re-makes their emails, after you confirm, so no scheduled email goes out on an older look; the API asks for an explicit acknowledgement naming the sends, and refuses while a scheduled send is within five minutes of firing. Their content and fire times are untouched, and a re-made send says so until it fires (SPEC §6, §9).
- The Template and Settings pages say, standing, whether the template and identity are in use by scheduled posts, ask before a save that would apply to their emails, and say afterward how many it applied to. A notice on the post and on the dashboard says when a template or identity change was applied to scheduled posts, until you clear it: the first use of the app's dismissible notice.

### Fixed

- A send too large for one sweep tick no longer shows a time to finish that ignores the wait between ticks: the estimate counts the ticks the rest needs, one a minute, so it no longer reads "ETA 26s" with two minutes to go, and the rate reads what a tick carries a minute rather than the burst just after one (SPEC §8).
- An edit typed while the editor was saving in the background read as saved without having been sent, and leaving the page then could lose it. It now stays unsaved and goes with the next save.
- A test or preview of a scheduled post sends its frozen copy, exactly as it will fire, and of a sent post its record, instead of a live render that could differ from either (SPEC §5).
- Two settings writers at once (the identity fields and the logo, or the editor and Claude) no longer overwrite each other's change.
- In the reference room, the tab for the page you are already on (and the Kestrel wordmark on the docs index) now scrolls back to the top instead of doing nothing.

## [0.1.0] - 2026-09-19

The first tagged release: a self-contained newsletter app on a Cloudflare Worker over D1 and R2, with a cron-driven send sweep and a swappable email provider.

### Added

- Markdown authoring with a single render path shared by preview, test, schedule, and send, so a clean test proves exactly what ships.
- Scheduling behind a cancelable review window: the render is frozen and the post soft-locked when scheduled, and stays cancelable until it fires. "Send now" runs the same path after a short cancelable buffer.
- Batched, idempotent delivery: a retry or restart never re-mails a recipient the provider already accepted.
- A double opt-in subscriber list the app owns end to end: consent, one-click unsubscribe, and suppression from bounces and complaints via provider webhooks.
- A permanent per-post public archive (view-in-browser), self-contained on the app's own origin, with an optional archive-on-your-apex enhancement.
- A public reader surface: landing page, archive index, and subscribe / confirm / unsubscribe.
- An admin editor and authoring API behind Cloudflare Access (human SSO plus a service token for Claude), with a local dev token for local-only development.
- Configurable publication identity (name, tagline, logo), email template, and confirmation-email wording, plus default test recipients. Preferences only, never secrets.
- A swappable email-provider seam with a fake in-memory transport for local dev and tests, alongside SES and Resend adapters.
- An in-app reference room: the setup guide and the API reference, served read-only inside the editor.
- A build-version stamp: every instance reports its version, commit, and build time, read-only in the editor and at `GET /api/version`.
- This changelog and a semantic-versioning release process.
