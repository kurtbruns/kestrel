# Working on the admin SPA

- Source: `client/` (TypeScript) and `public/` (index.html, styles.css, _headers, favicon).
- Served: `dist/public`, generated by `scripts/build-client.mjs`, gitignored, rebuilt at will.
- Edit the source, never `dist/`: a hand patch there lasts until the next build.
- Nothing tracked carries a build artifact's hash.
- Code the Worker also needs comes from `../shared` (slug, archive URL, wire types), never from `src/`: `shared/` is runtime-neutral and dependency-free, and its plain-Node test project is what keeps it so. Do not hand-mirror a Worker function in `client/`; move it to `shared/`.

## What the build emits

- `public/` copied through: the hand-authored `styles.css` (esbuild never touches it), `_headers`, favicon.
- `client/main.ts` bundled to one framework-free, dependency-free, plain-JS `app.js`.
- `index.html` generated from its source with each asset's content hash as its `?v=`. If the source loses a `./app.js` or `./styles.css` reference the build fails loud rather than serve a stale asset.
- `public/_headers` caches those two paths immutably, so a changed asset is always a new URL.
- Stable filenames with a `?v=`, not esbuild's hashed filenames: observed under wrangler 4.129, `wrangler dev` never serves a file added to the assets directory after startup (a rewritten file is served fresh; a new one 404s until restart), so a new filename per rebuild would kill the dev loop. Wrangler's own assets watcher is meant to cover that, so this is its bug, not its design; stable names are the right production cache shape regardless. This is also why `_headers` is a plain static file.

## Flavors

- Production, the default and what a deploy gets: minified, `__DEV__` false, dev-only code compiled out.
- Dev, `--dev` or `KESTREL_CLIENT_DEV=1`: readable, `__DEV__` true. `scripts/dev.mjs` sets the variable for every builder it starts, including wrangler's `build.command`, which takes no flag.
- Declare a new build constant in `client/globals.d.ts`.
- Both flavors link a sourcemap: readable stack traces from a deployed editor are worth the file, which sits behind Access with the rest of `/dashboard`.

## Where the build runs

- `npm run dev`: the watch, which rebuilds on `client/` edits (~10 ms) and re-emits on `public/` edits.
- Wrangler's `build.command`, so a bare `wrangler deploy` can never ship a stale tree. `watch_dir` is pinned to `src/` so `wrangler dev` does not double-build client edits.
- `pretest`, as `--check`: the bundle is built in memory and the source `index.html`'s asset references verified, nothing written. The tests never load the tree, and a gate run in a second terminal beside a live `npm run dev` must not overwrite the dev tree with the production flavor (the open editor would reload onto a bundle with no live reload in it).
- `wrangler types` runs `build.command` too; the script exits at once when `WRANGLER_COMMAND` is `types`, for the same reason. Only an explicit `npm run client:build` or a deploy writes the production flavor.

## Types and tests

- `client/tsconfig.json` extends the root with the DOM lib and no Worker or Vitest types; `npm run typecheck` runs it as a second program.
- Layout: a feature folder per part of the publication — `posts/` (the drafts list, the editor, and its autosave, dirty, and revision logic), `sends/` (the list, the record, the shared `progress` helpers, the resolve and reschedule `dialogs`), `subscribers/` (the list, the add and unsubscribe `dialogs`), `settings/` (settings, the template page, the re-make flow), `dashboard/`, and `room/` (docs, the API reference, the room's `shell`) — each holding its views, its dialogs, and its pure logic. What is flat in `client/` is the app itself: `main`, `state`, `lifecycle`, `router`, `shell`, `auth`, `api`, `dev_reload`, the two reads every feature makes, `deployment` (the deployment reflection) and `brand` (the sidebar brand), and `send_state`, the send-state layer the dashboard, the send pages, and the post pages all follow sends through (flat because it is shared across features and holds app-wide state: one read, one cadence, for every follower). One more folder, `ui/`, holds what the views are built from and knows no feature and no route: the primitives (`html`, `dom`, `icons` with its `.svg` files, `format`: pure formatting and parsing) and the shared widgets (`widgets`: toast, clipboard, badge, modal, tooltip, menu, busy, error view; `notice`; `savebar`; `list_controls`; `highlight`). Its membership test is what keeps it from becoming a junk drawer: a `ui/` module imports `ui/`, `shared/`, and the shell's roots, nothing else of the app (a widget that lives for a mount, the save bar, takes the mount's `AbortSignal` and listens on it directly, so it needs nothing from `lifecycle`). Names inside a folder drop the folder's word (`sends/list.ts`), except a folder's namesake view (`dashboard/dashboard.ts`, `settings/settings.ts`). Specs sit beside their module; the harness is `client/test/`.
- Every module is strict; nothing carries `// @ts-nocheck`. `main.ts` is the entry: `boot()` installs the shell, the tooltips, the room bar, and the router (`installShell()`, `installTooltips()`, `installRoomBar()`, `installRouter()`, each a named call in that one function), then probes identity and routes. A new route's response shape is defined in `shared/` and the Worker route is typed against it in the same change, so the compiler holds both ends.
- App-wide state (the token, the session, the settings payload) lives in `appState` (`client/state.ts`); everything a view owns lives in the view, for the life of its mount. A `let` only one module touches stays in that module; never export a mutable `let` (ES modules cannot assign another module's binding).
- The view lifecycle is `client/lifecycle.ts`: `mount(view)` tears the mounted view down and starts the next in a fresh root under `#app` with an `AbortSignal` that ends with it; `router.ts` mounts what the hash names, and a view re-enters itself (a reload, a retry) through `mount()` too, never by calling its render function. A view is `(root, signal) => handle?`: it paints into `root`, never into `#app`, and binds what it starts to `signal`, so what could outlive it cannot: a ticker is `every(ms, fn, signal)`, a repeating read is `poll(ms, tick, signal)` (a tick answers `false` to stop), a page that shows a send follows it through `send_state` (`followSends`, `followSend`) and never polls one of its own, a borrowed control such as the save bar takes the signal, and a read that paints passes `{ signal }` to `api()` so navigating away cuts it off. A write never takes the signal: a save the reader started must land whether or not they stayed to watch. After an `await`, the root may be stale; a paint into it is harmless (detached), but a redirect is not, so `if (signal.aborted) return;` before a `location.hash =`.
- What a view offers the app around it is the `ViewHandle` it returns: `dirty()` for the unload prompt, `beforeLeave()` (answer `"leave"` after saving in the background, or `"confirm"` to have the router ask first), `manualSave()` for ⌘S. The router reads the mounted handle; no view state crosses a module boundary any other way.
- Imports run one way, with no cycle anywhere: a feature imports the flat modules and `shared/`, never `src/`; a flat module never imports a feature, except the two that wire features in, `main.ts` (installs) and `router.ts` (mounts); a feature imports another only through that feature's exports of shared pieces (the dashboard composes the others; the editor opens the sends' reschedule dialog), and never in a cycle. Checkable with an import-graph pass. Keep it so: a cycle works only until a top-level statement reads across it, because esbuild hoists module scopes into one and that read sees `undefined`.
- No module does anything at load but define things. A listener that outlives a render is registered by an `install…()` that `boot()` calls; one a single view owns (the docs fold's media query) registers on that view's first render. `shell`'s root and control lookups are the one load-time read, and they read the document, not another module. Checkable: `grep -rn addEventListener client --include='*.ts'` finds no call at module scope.
- A module's header names one responsibility. A header that needs "and" twice is two modules; `ui/widgets` and `ui/format` are catalogs of small independent pieces, not a place for a subsystem.
- Client specs (`client/**/*.spec.ts`) run in the `client` Vitest project under happy-dom with file loading off, since an inserted `<link>` would otherwise be fetched for real. The Worker suite is the `worker` project on the workerd pool, untouched.
- Every client spec starts with the real admin shell in the document: `client/test/setup.ts` loads the body of `public/dashboard/index.html` before the spec's imports, because the shell module reads its roots at import time.
- A view test runs the real view over a scripted API: `fakeApi(routes)` from `client/test/support.ts` replaces the global `fetch` (the only network the editor has), so `api()` itself runs, with its credential and its error shaping, and a read carrying the mount's signal is cut off the way the real fetch cuts it off. Mount the view the way the router does (`mount(renderDrafts)`, or `mount((r, s) => renderEditor(id, r, s))`), `settle()`, query the DOM, click, assert; assert `fake.unhandled` is empty; `unmount()` is what navigating away does, and `mounted()` is the handle the router sees. `posts/drafts.spec.ts` is the pattern.
- Nothing in a client spec reaches the Worker or its bindings; `client/test/` is imported by specs only and never enters the bundle.
- `send_state` is how a page keeps up with sends (docs/DESIGN.md §9): one shared read of `GET /sends/feed`, armed at the `read_again_at` the server gives (by the server's clock, `now`), paused while the tab is hidden and read at once on return (its visibility listener lives exactly as long as it has a follower), backed off quietly on a failed read. A page follows from its own read: `followSends` takes the `GET /sends` response (its cursor and rows), `followSend` the `GET /sends/:id` response, so the first feed read starts where the page's read stood; followers that joined with different cursors share one read from the earlier (`earlierCursor`). A follower gets each later read that changed something, with the stage changes; `readSendsNow()` is for a page that has just acted. The pace is the server's (`src/send/feed.ts`, under test); the layer never keeps one of its own.
- The editor's timing and concurrency decisions are pure modules with their own specs: `autosave.ts` (the idle and hard-cap timers), `dirty.ts` (what is saved is what was sent), `revisions.ts` (the base revision, and what a 409 or a freshness poll means against it). The view wires them; a change to how saving behaves starts there, under test.

## Markup

- Build markup with the `html` tag (`client/ui/html.ts`). Every interpolation is escaped unless it is already `Html`; arrays flatten; `null`, `undefined`, and `false` render nothing; `true` is a compile error.
- Escaping makes two contexts safe: text, and a quoted attribute value whose meaning is text. An interpolation in an unquoted attribute value throws.
- Escaping does nothing for a value that is code or a URL. Not `href`, `src`, `action`, `formaction` (a `javascript:` URL has no character to escape; check the scheme before interpolating one from publisher or subscriber data), not `srcdoc`, `style`, or an `on*` handler, and never inside `<script>` or `<style>`, an attribute name, or a tag name.
- A function that returns markup returns `Html`, never `string`, so it composes without double escaping and the checker rejects a plain string where markup is expected. `Html` is nominal: a look-alike object is rejected at compile time and at runtime.
- Markup reaches the document through `setHtml(el, markup)`, the one place strings meet `innerHTML` in converted code. It throws on anything that is not `Html`.
- `unsafeHtml(s)` is the only way in for markup the tag did not build: server-rendered HTML from the API (the docs), or markup a module builds by string (the highlighters, the sample-email preview, which escape first and decorate after). Grep for it when auditing.
- A bare attribute (`disabled`, `hidden`, `readonly`) is markup, not text: spell it once as `html\` disabled\`` and interpolate that, never a string.
- Never interpolate an `escapeHtml()` result into `html`: it is escaped twice. `escapeHtml` is for text that will land in a page the tag does not build (the embed snippet a publisher pastes into their own site).

## Icons

- An icon is a file: `client/ui/icons/<name>.svg`, a complete SVG (`xmlns`, its own `viewBox`, `aria-hidden="true"`, `currentColor` where it should follow the text) that opens in any viewer and diffs as a drawing.
- `client/ui/icons.ts` is the registry: it imports every file as text and `icon(name)` returns it as `Html`. Add an icon by adding the file and one import + entry there; `IconName` then knows it.
- The build inlines the files (esbuild's `text` loader); the client test project mirrors that with the `svg-as-text` plugin in `vitest.config.ts`, so a spec that imports a module using icons gets the same markup. Keep the two in step.
- The sidebar's sprite in `public/dashboard/index.html` is the one exception: it paints before any script runs. A generated image (the letter avatar) is code, not an icon.

## Live reload in the dev flavor

- `client/dev_reload.ts` polls the served `index.html` once a second and compares its `?v=` stamps to the ones the page loaded with.
- A new `app.js` stamp reloads the page, once: a declined leave prompt is not re-asked.
- A new `styles.css` stamp hot-swaps the `<link>`, so editor state survives a CSS tweak.
- It fetches with cache mode `reload` on purpose: `wrangler dev` serves a regenerated `index.html` under its original ETag, so a plain reload would revalidate to a 304 and keep the stale page.
